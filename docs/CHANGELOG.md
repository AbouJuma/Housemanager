## Phase B

### Module 7 — Integrations Center (2026-08-02)

- Built the `integrations` table + `Integration` model (encrypted `credentials` via Laravel's `encrypted:array` cast — plain `TEXT` column, not `JSON`, since the cast encrypts the whole JSON-encoded string and ciphertext isn't valid JSON) and the full CRUD/hub UI the master prompt's Integrations Center spec calls for, **ahead of any actual gateway driver** — those land in Modules 8–11 (Storage, Email, SMS, Payment).
- **One generic credential form for every provider, not a schema per provider**: the master prompt's own field list (Enable/Disable, Sandbox/Production, API Key, API Secret, Merchant ID, Username, Password, Webhook URL, Callback URL, Test Connection, Save) is uniform across every gateway/SMS/email/storage/map/AI provider named in the spec, so `config('integrations.types')` only declares which providers exist per type — no per-provider field metadata needed. All 6 types and every named provider (Stripe/PayPal/Flutterwave/Selcom/NMB/CRDB/NBC/Airtel Money/M-Pesa/Tigo Pesa/HaloPesa/AzamPay for payments; Beem/Infobip/Twilio/ClickSend/Africa's Talking/NextSMS for SMS; SMTP/Gmail/Microsoft 365/Mailgun/SendGrid/SES for email; Local/S3/R2/Spaces/GCS for storage; Google Maps/Mapbox/OSM for maps; OpenAI/Anthropic/Gemini/DeepSeek/xAI for AI) are in the catalog today. Deliberately skipped: "Government APIs"/"WhatsApp"/"Mobile Apps"/"Future APIs" sections the spec's menu structure mentions with no concrete provider list — adding an empty section would be dead UI; add one when there's a real provider to put in it (zero code changes needed elsewhere, which is the whole point of the catalog).
- Blank credential fields on save mean "leave unchanged" — the form never re-displays a decrypted secret to type over — so `IntegrationService::save()` merges onto the existing `credentials` array rather than replacing it wholesale.
- **"Test Connection" is honest, not faked.** Added `App\Modules\Integrations\Contracts\IntegrationTester`, the contract a real driver implements, and `config('integrations.testers')` (provider → tester class), which starts **empty**. Until a module registers a tester for a provider, clicking Test Connection sets `status = 'untested'` and plainly reports that no tester exists yet, rather than pretending to validate credentials against an API that isn't wired up.
- `IntegrationPolicy` follows the `RolePolicy`/`SettingsPolicy` pattern (SaaS-owner staff don't bypass — an integration only makes sense within one company). Added `integrations.view`/`integrations.update` to the permission catalog; `PermissionSeeder`'s existing resync mechanism (from Module 4) picked them up for every already-seeded company's `Admin` role automatically.
- Routes are shaped `/integrations/{type}/{provider}`, not a per-row id — the controller always resolves via `(company_id, type, provider)`, so there's no id a company admin could guess to reach another company's row even before the policy check runs. Verified this directly: a second company's admin loading `/integrations/payment/stripe/edit` sees a blank form, never the first company's saved API key.
- Verified end-to-end against real MySQL over live HTTP: saved real credentials through the form, confirmed the `integrations` table stores ciphertext (not plaintext) via a raw query, and confirmed a second company's admin cannot see the first company's saved values at the same URL.
- 177 passing tests total (30 new: encrypted round-trip and plaintext-never-stored on the model, credential-merge/unknown-provider/tester-registration behavior on the service, `IntegrationPolicy`'s company boundary, and the web hub/edit/test flows including the cross-company isolation check).

### Module 10 — SMS Framework (2026-08-02)

- Built `App\Modules\Sms`: the first Phase B module needing the actual `*ProviderInterface`/`*Manager` pattern from ARCHITECTURE.md §5, since — unlike Storage/Email — Laravel ships no shared transport for SMS and every gateway is a genuinely different HTTP API.
- Added `App\Modules\Sms\Contracts\SmsProviderInterface` (`send(Integration, $to, $message): array{success, message, message_id?}`) and one driver per catalog provider in `App\Modules\Sms\Drivers`: `TwilioDriver`, `InfobipDriver`, `ClickSendDriver`, `AfricasTalkingDriver`, `BeemDriver`, `NextSmsDriver`. Five of the six also implement `IntegrationTester` directly (no separate resolver layer needed — a driver already reads its own credentials off the `Integration` it's given), doubling as both the real send capability and the Test Connection check.
- Added `App\Modules\Sms\Services\SmsManager::send(Company, $to, $message)` — resolves a company's active `type = 'sms'` integration and delegates to its driver via the new `config('integrations.sms_drivers')` map (all six providers; separate from `config('integrations.testers')`, which only lists the five with a verification check — see below). Returns a failure result rather than throwing when no provider is active or no driver is registered, matching the array-result shape every caller already expects.
- **Field mapping is genuinely provider-specific**, unlike Storage/Email's one-mapping-fits-the-type approach: Infobip's account-specific base URL is mapped onto the otherwise-unused `username` field; ClickSend and Africa's Talking each swap which of `api_key`/`api_secret` holds the username-shaped vs. secret-shaped credential. Each driver's docblock documents its exact mapping; the shared 5-field form itself stays as-is, with type-level labels honest enough to span all six (`API Key / Account SID / Username`, etc.) rather than claiming per-provider precision the generic form can't deliver.
- **Confidence documented per provider, not assumed uniform.** Twilio/Infobip/ClickSend/Africa's Talking are built against long-stable, well-referenced public APIs. Beem is implemented to the best of publicly available documentation but flagged as unverified against a live account. **NextSMS deliberately does not implement `IntegrationTester`** — no dedicated credential-check endpoint was confident enough to present as real verification, so it's absent from `config('integrations.testers')` and Test Connection honestly falls through to Module 7's "no tester yet" message, the same honesty principle as GCS in Module 8.
- **No live smoke test against a real SMS provider** — unlike Storage/Email, sending a real SMS costs real money and reaches a real phone number; without real credentials or authorization to spend against them, no live send/verify was attempted against any actual gateway. Verified instead: all 28 new tests run against `Http::fake()` (zero real network egress from any driver test), plus a database-only check that `integrations.credentials` round-trips encrypted for `type = 'sms'` rows.
- 230 passing tests total (28 new: two send-success/failure cases and, where applicable, two test-success/failure cases per driver, plus `SmsManager`'s no-active-provider/inactive-integration/delegation/full-catalog-resolution behavior).

### Module 11 — Payment Framework (2026-08-02)

- Built `App\Modules\Payments`: `App\Modules\Payments\Contracts\PaymentGatewayInterface` (`charge`/`verify`/`refund`, integer minor units/cents throughout - never a float for money) and `App\Modules\Payments\Services\PaymentManager`, the same `*ProviderInterface`/`*Manager` shape as SMS (Module 10). `charge()` uses a company's currently active gateway; `verify()`/`refund()` instead target an explicit provider, since they act on a transaction already charged through a *specific* gateway that might since have been switched off.
- **Confidence was calibrated more conservatively than SMS**, because this module moves real money - a subtly wrong signature scheme or endpoint here is a worse failure mode (a miscounted payment, a refund aimed at the wrong transaction) than a text message that doesn't send. Only **Stripe, PayPal, and Flutterwave** got full real drivers, built against stable, extensively-referenced public REST APIs with simple Bearer-token or Basic-Auth-then-Bearer authentication. The other **nine** catalog providers (Selcom, NMB, CRDB, NBC, Airtel Money, M-Pesa, Tigo Pesa, HaloPesa, AzamPay) route through one shared `App\Modules\Payments\Drivers\VendorIntegrationRequiredDriver` that makes **no API call of any kind** and reports plainly that real vendor integration work is needed - Selcom's custom HMAC request-signing scheme and the bank-proprietary providers (NMB/CRDB/NBC typically aren't public self-service APIs at all) aren't something this app can confidently reproduce without a live account to verify against. No `IntegrationTester` registered for those nine either, so Test Connection correctly falls through to Module 7's honest "no tester yet" message.
- `charge()`'s real shape for card gateways is a hosted-checkout redirect, not an inline charge: Stripe's driver creates a Checkout Session, PayPal's creates an Order and returns its approval link, Flutterwave's returns a payment link - the correct, honest capability an unauthenticated backend integration can actually offer today, since no Stripe.js/PayPal-JS frontend exists yet (no Tenant Portal until Phase E). ## Phase D

### Module 19 — Accounting (2026-08-09)

- Built `App\Modules\Accounting`, the first Phase D module: a standard three-table double-entry ledger (`accounts`, `journal_entries`, `journal_entry_lines`). `Account.type` drives `Account::balance()`'s sign convention (debit-normal for asset/expense, credit-normal for liability/equity/income). `journal_entry_lines.account_id` uses `restrictOnDelete()`, the same reasoning as `leases.tenant_id`/`unit_id` — real ledger history can't be hard-deleted out from under an account.
- `JournalEntryService` deliberately does not extend `BaseService` and has no `update()` — a posted entry is immutable. Correcting a mistake means `void()`, which posts a real reversing entry (every line's debit/credit swapped) and marks the original `voided`, never edits or deletes history. Because of this, `Account::balance()` never filters by entry status — a voided entry's reversal already nets it to zero on its own.
- `JournalEntryService::post()` validates that every entry's lines balance and total more than zero before persisting anything; `StoreJournalEntryRequest` additionally rejects any single line that's both a debit and a credit, or neither, at the HTTP layer.
- The real payoff: revenue and cash receipts now post themselves automatically. Added `Invoices\Events\InvoiceSent`/`InvoicePaymentRecorded`, dispatched by `InvoiceService::send()`/`recordPayment()` after their transactions commit (never from inside one, so a bookkeeping-side failure can never roll back the invoice action itself) — Invoices has zero knowledge that Accounting listens, the same decoupling `Companies\Events\CompanyCreated` already established for Module 3's default-role seeding. `PostInvoiceRevenueJournalEntry` posts `Dr Accounts Receivable / Cr Rental Income` on send; `PostInvoicePaymentJournalEntry` posts `Dr Cash or Bank / Cr Accounts Receivable` on payment (choosing Cash vs. Bank by payment method). Both listeners fail soft — if a company's default accounts have been renamed/deactivated/deleted, they log a warning and skip, never blocking the actual invoice action.
- `accounts.*` and `journal-entries.*` are two separate permission groups (mirroring the `leases.*`/`invoices.*` split), not one combined group — a bookkeeper posting entries and someone restructuring the chart of accounts are different enough responsibilities to grant independently. `journal-entries.void` is its own permission rather than folded under `update`, since there's no `update` action on a journal entry to fold it into.
- Added `SeedDefaultChartOfAccountsForCompany`, triggered by `Companies\Events\CompanyCreated` (the same trigger as Module 3's default roles) — every new company gets a ready-made 12-account starter chart automatically. Added `ChartOfAccountsSeeder` as a one-time backfill for companies that existed before this module did (the same role `PermissionSeeder` plays for permission catalogs), and ran it against the real database.
- Documented a real, deliberate limitation: this module does not retroactively post journal entries for invoices sent/paid before it existed, since `InvoiceSent`/`InvoicePaymentRecorded` only fire at the moment those actions actually run. New activity going forward is fully covered.

### Module 20 — Expenses (2026-08-10)

- Built `App\Modules\Expenses`: `Expense belongsTo Account` directly (not via an event) - the first module to genuinely *consume* Accounting rather than be consumed-from by it, the same normal dependency direction Rent Collection has toward Invoices/Payments (§11). Posts its ledger entry immediately at creation, no draft/send lifecycle - an expense is a fact being recorded, not a document sent for approval. Unpaid: `Dr {category} / Cr Accounts Payable (2000)`. Paid: `Dr {category} / Cr Cash (1000) or Bank (1100)`, chosen by payment method.
- `vendor_name` is free text, not a `vendor_id` FK - the Vendors module (Module 21) doesn't exist yet, the same deferred-FK discipline as `properties.landlord_id`. `property_id` is nullable - not every expense is property-specific.
- `payment_status` (unpaid/paid) and `status` (active/voided) are two separate lifecycles. `markAsPaid()` posts a real second settlement entry (`Dr Accounts Payable / Cr Cash or Bank`), not a correction. `void()` reverses *every* journal entry an expense ever posted (initial + settlement, if it happened) - an expense marked paid and later voided needs both halves of its ledger history reversed. Both reuse Accounting's own `JournalEntryService::post()`/`void()` rather than reimplementing balance/reversal logic.

Correcting an amount means voiding and re-recording, not editing in place.

### Module 23 — Inventory (2026-08-13)

### Module 29 — Subscriptions & Billing (2026-08-19)

- Built `App\Modules\Subscriptions`: a `subscription_plans` catalog, each company's `subscriptions` (an immutable history table, the same convention as `journal_entries`/`inventory_transactions` - a plan change or renewal always inserts a new row, never mutates one), and the SaaS owner's own `subscription_invoices` billing companies for their subscription - a distinct sequence from Module 17's tenant-facing `invoices`. `Company::currentSubscription()` resolves "current" as whichever row was created most recently.
