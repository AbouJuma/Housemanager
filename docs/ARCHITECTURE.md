# Architecture — Real Estate ERP SaaS

Source of truth for the system's software, database, module, and integration architecture. Updated as each module lands; never regenerated from scratch.

## Hosting Constraint

Must run on shared hosting (Apache/cPanel/DirectAdmin): no Redis, Docker, Supervisor, Horizon, Node in production, or WebSockets. Must also scale to thousands of companies and millions of records. These are reconciled by: a single database with strict row-level tenant isolation (not database-per-tenant), cron-driven queue processing instead of persistent workers, and an interface-driven integration layer so swapping providers or later moving to a beefier host never requires rewriting business logic.

## 1. Core Architectural Decisions

| Decision | Choice | Reasoning |
|---|---|---|
| Tenancy model | Single database, shared schema, row-level isolation via `company_id` + global Eloquent scope + request-bound tenant context | DB-per-tenant isn't viable on shared hosting; row-level isolation with indexing on `(company_id, ...)` scales to millions of rows on MySQL 8. |
| App structure | Modular monolith, custom lightweight module loader (no third-party module package) | Keeps dependencies inside the approved stack; modules self-register with zero core-file changes. |
| Background jobs | `database` queue driver, no Horizon/Supervisor | `php artisan schedule:run` is the only cron entry cPanel needs; scheduler drains the DB queue in short bursts. |
| Caching/sessions | `database` cache & session drivers | No Redis/Memcached assumed; config is driver-swappable via `.env` only. |
| Primary keys | `BIGINT UNSIGNED AUTO_INCREMENT` internally, `uuid` column (unique, indexed) exposed externally | Fast joins internally; non-enumerable public identifiers. |
| Soft deletes | On all business tables | Audit trail and recoverability for financial/lease records. |
| Asset pipeline | Vite at build time only; compiled `public/build` deployed | Satisfies "no Node in production." |
| API | Laravel Sanctum, `/api/v1/*` | Works on shared hosting, unlike Passport. |
| Secret storage | Laravel `encrypted` Eloquent cast on integration credential columns | Uses `APP_KEY`-based encryption, no external KMS. |
| PHP version | `^8.2` (spec called for 8.3+; this environment's available PHP is 8.2.12) | Laravel 12 fully supports 8.2. Production hosting should still target 8.3+ where the host offers it — no 8.3-only syntax is used, so upgrading later is a no-op. |
| Frontend build | Bootstrap 5 + Bootstrap Icons + SweetAlert2 + DataTables + Select2 + Chart.js + ApexCharts via npm/Vite, compiled to `public/build` | Matches the spec's frontend stack exactly; Node never runs on the production server, only at build time (Module 2). |
| API URI prefix | `App\Core\Foundation\ModuleServiceProvider` always mounts a module's `Routes/api.php` under `api/v1` with the `api` middleware group | Laravel 11+'s minimal skeleton doesn't auto-prefix `api.php` the way the old `RouteServiceProvider` did; a module forgetting this fails silently with 404s, so it's enforced once in Core rather than left to each module (found the hard way in Module 2). |
| RBAC | Spatie Permission with the **teams** feature, `team_foreign_key` = `company_id` (not the default `team_id`) | Roles/permissions are scoped per company for free using the package's own mechanism, with column naming that matches the rest of the schema. |
| Self-registration | Not exposed — no public `/register` route | A self-registered user has no `company_id`, which per the tenancy model makes it a SaaS-owner-tier account. Real users are provisioned by an authenticated SaaS-owner/company-admin through the Users module. |

**Model-event caveat**: `HasUuid`/`BelongsToCompany` rely on Eloquent's `creating` event. Anything that disables model events (`Illuminate\Database\Console\Seeds\WithoutModelEvents`, `Model::withoutEvents()`) will silently insert rows with a `NULL` `uuid`/`company_id` and fail the DB's `NOT NULL` constraint. `database/seeders/DatabaseSeeder.php` intentionally does **not** use `WithoutModelEvents` — keep it that way, and don't add it to a module seeder either. `tests/TestCase.php` seeds the permission catalog in `setUp()` for the same reason: Spatie's `hasPermissionTo()` throws for an unregistered permission name rather than returning false, so it has to exist before any policy check runs.

**Spatie Permission teams caveat**: the *current* team id (`Spatie\Permission\PermissionRegistrar::getPermissionsTeamId()`, kept in sync with `CompanyContext` by `IdentifyCompany`) governs every `hasPermissionTo()`/`assignRole()`/`Role::create()`/`Role::findOrCreate()` call — never the target model's own `company_id`. Acting across companies (a SaaS-owner assigning a role to a user in company X, or seeding a new company's default roles) requires explicitly switching context first via `App\Core\Tenancy\PermissionsTeam::runAs($companyId, $callback)`. Separately, Spatie's `Role`/`Permission` models apply **no** automatic scope on plain queries (`Role::all()`, `Role::count()`, …) — only `create()`/`findOrCreate()`-style calls read the current team id. Any manual `Role` query must filter `company_id` explicitly (see `App\Modules\Users\Services\RoleService`).

## 2. Folder Structure

```
app/
  Core/                      # cross-cutting kernel — see "Core Kernel" below
  Modules/
    {ModuleName}/
      Models/ Repositories/ Services/ Http/Controllers/ Http/Requests/
      Http/Resources/ Policies/ Events/ Listeners/ Jobs/ Observers/
      Providers/{ModuleName}ServiceProvider.php
      Database/Migrations/  Routes/web.php  Routes/api.php
      Resources/Views/  Resources/Lang/
  Support/
    Payments/  { PaymentGatewayInterface, PaymentManager, Drivers/ }
    Sms/       { SmsProviderInterface, SmsManager, Drivers/ }
    Maps/      { MapProviderInterface, MapManager, Drivers/ }
    Ai/        { AiProviderInterface, AiManager, Drivers/ }
resources/
  views/ (layouts/, components/, plus each module's own view namespace)
  js/ css/
database/ migrations/ seeders/ factories/   # framework-level tables only
docs/
  ARCHITECTURE.md INSTALL.md DEPLOYMENT.md USER_MANUAL.md
  DATABASE_SCHEMA.md API_DOCUMENTATION.md CHANGELOG.md
```

A module is entirely self-contained under `app/Modules/{Name}`: its own migrations, routes, views, and a `{Name}ServiceProvider` that `App\Core\Foundation\ModuleManager` discovers and registers automatically (see Core Kernel). Dropping a new module's folder in place is the entire integration step — nothing in `app/Core`, `bootstrap/`, or another module needs to change.

## 3. Core Kernel (`app/Core`) — built in Module 1

| Class | Responsibility |
|---|---|
| `Tenancy\CompanyContext` | Request-scoped holder of the "current company id" (bound as a singleton). `CompanyContext::id()` is the static read accessor. |
| `Http\Middleware\IdentifyCompany` | Resolves `company_id` from the authenticated user and sets it on `CompanyContext`. Registered as the `identify.company` route middleware alias; modules attach it to their authenticated route groups. |
| `Concerns\BelongsToCompany` | Eloquent trait: adds a global scope filtering every query to the current company, and stamps `company_id` on new records. `scopeForCompany()` explicitly bypasses the tenant scope (SaaS-owner tooling only). `company()` relation resolves against `config('tenancy.company_model')`. |
| `Concerns\HasUuid` | Eloquent trait: generates a `uuid` on creation if not already set; `getRouteKeyName()` returns `uuid` so routes/URLs never expose the internal auto-increment id. |
| `Repositories\RepositoryInterface` / `BaseRepository` | Generic CRUD contract (`all`, `paginate`, `find`, `findOrFail`, `findByUuid`, `create`, `update`, `delete`) every module repository extends. |
| `Services\BaseService` | Wraps repository `create`/`update`/`delete` calls in `DB::transaction()`; module services extend this for the transactional default and add business logic on top. |
| `Foundation\ModuleServiceProvider` | Abstract base every module's provider extends; auto-loads that module's `Database/Migrations`, `Routes/{web,api}.php`, `Resources/Views`, `Resources/Lang` by convention. |
| `Foundation\ModuleManager` | `discover(string $path)` scans a modules directory for `{Name}/Providers/{Name}ServiceProvider.php` and returns the FQCNs; `register($app)` discovers under `app/Modules` and registers each with the container. Called once from `AppServiceProvider::register()`. |
| `Tenancy\PermissionsTeam` | *(added Module 3)* `runAs(?int $companyId, callable $callback)` temporarily switches Spatie Permission's current team id, runs the callback, and restores the original id afterward (even if the callback throws) — see the teams caveat above. |

`config/tenancy.php` holds `company_model`, pointed at `App\Modules\Companies\Models\Company::class` — satisfied by Module 2, so `BelongsToCompany::company()` now resolves for every later module.

`IdentifyCompany` is registered globally on the `web` middleware stack (`bootstrap/app.php`) rather than per-module — safe because the session guard resolves `$request->user()` lazily regardless of middleware order. The same isn't true for Sanctum: `$request->user()` only reflects the token-authenticated user *after* `auth:sanctum` has run (that middleware calls `Auth::shouldUse()`), so appending `IdentifyCompany` globally to the `api` group would run too early and silently break tenant scoping for every API request. Modules instead use the `api-tenant` middleware group (also defined in `bootstrap/app.php`: `['auth:sanctum', IdentifyCompany::class]`, in that order) on their protected API routes.

## 3a. Companies (`app/Modules/Companies`) — built in Module 2

The tenant root itself, so it does **not** use `BelongsToCompany` (it has no `company_id`) but does use `HasUuid`. `Company` implements Spatie Media Library's `HasMedia` for branding (`logo`/`favicon` single-file collections) plus scalar `primary_color`/`secondary_color`. `CompanyService` auto-generates a unique slug from the name (falls back to `-1`, `-2`, ... suffixes on collision) and defaults new companies to a 14-day `trial` status.

Authorization (`CompanyPolicy`) implements the SaaS-owner-vs-tenant split from `docs/ARCHITECTURE.md`'s tenancy model directly: a user with `company_id === null` (SaaS-owner staff) can manage every company; a user with a `company_id` can only view/update the one company they belong to, and can never list all companies or create/delete one. Full CRUD ships both as Blade-rendered web routes (`companies.*`, Bootstrap 5 views with SweetAlert2 delete confirmation) and a versioned JSON API (`api.v1.companies.*` under `/api/v1/companies`, Sanctum-guarded).

`CompanyService::create()` dispatches `App\Modules\Companies\Events\CompanyCreated` after the transaction commits — Module 3's `SeedDefaultRolesForCompany` listener hooks this to seed the new company's default roles. Seeders that create companies via `Company::factory()->create()` bypass the service (and therefore the event) entirely, since factories are direct Eloquent creation; `CompanySeeder` dispatches it manually so seeded companies end up in the same state a real signup would produce.

## 3b. Users, Roles & Permissions (`app/Modules/Users`) — built in Module 3

Real authentication via Laravel Breeze's Blade stack (`php artisan breeze:install blade`), fully reskinned to Bootstrap 5 — Breeze's own Tailwind/Alpine views and components were replaced, and the Tailwind/Alpine packages it added to `package.json` were removed. Two flows Breeze scaffolds by default were deliberately **not** kept:

- **Self-registration** — see the "Self-registration" row in §1. `RegisteredUserController`, its routes, and its view were deleted.
- **Email verification** — needs a real mailer (Phase B, not built yet) and doesn't fit an admin-provisioned-user model where an admin already vouches for the account at creation. `EmailVerification*Controller`, `VerifyEmailController`, their routes, and the verify-email view were deleted; `User` never implements `MustVerifyEmail`.

`App\Models\User` (kept at the standard Laravel path, not moved into the module, so Breeze/Sanctum/`config('auth.providers')` keep working unmodified) gained: `uuid` + `company_id` columns (migration owned by this module, since it alters a Module-1 table), the `BelongsToCompany`/`HasUuid` traits, Spatie's `HasRoles` trait, `isSaasOwner(): bool` (`company_id === null`), and `roleNamesForOwnCompany()` (see the teams caveat in §1 — reading a user's roles from a different team context, e.g. a SaaS-owner's cross-company list view, needs this instead of `getRoleNames()` directly).

**Permission catalog**: `config/permissions.php` is the single source of truth, grouped by owning module (`users.*`, `roles.*` so far); `PermissionSeeder` reads it and creates the (global, non-team-scoped) `Permission` rows. Each future module adds its own group as it's built.

**Authorization** (`UserPolicy`, `RolePolicy`) both combine a Spatie permission check with an explicit same-company comparison — having a permission never lets you touch another company's data. `RolePolicy` is the one policy in the app where SaaS-owner staff do **not** bypass the check: a role only makes sense within a specific company's team scope, and the SaaS owner has no "current company" to manage roles within. Bootstrapping a new company's first roles happens automatically (§3a); the SaaS owner can still assign an existing role to any user via the Users edit page (which explicitly switches team context), just not browse a standalone role editor cross-company. A user can never delete their own account through this UI.

**Default roles**: `SeedDefaultRolesForCompany` (listening for `CompanyCreated`) gives every new company an `Admin` role (every permission) and a `Staff` role (every `*.view*` permission).

Full CRUD ships for Users (web `users.*` + API `api.v1.users.*`) and for Roles (web `roles.*` only — no API yet, a deliberate scope cut; add one if a headless client needs role management before it's otherwise built). Both follow the Companies module's UI conventions (Bootstrap 5, SweetAlert2 delete confirmation, paginated + searchable index).

## 3c. Settings (`app/Modules/Settings`) — built in Module 4

A generic key/value registry (`settings` table: `company_id` nullable + `key` + JSON `value`) so any module can read/write a setting by adding one entry to `config/settings.php` — no migration of its own needed. `company_id === null` rows are system-wide (SaaS-owner scope); everything else belongs to exactly one company. Deliberately **not** built on `BelongsToCompany`: that trait's binary "belongs to a tenant" model doesn't fit a table whose `NULL` means "system-wide" rather than "unassigned," so `SettingsService` handles both scopes explicitly instead.

`SettingsService::get{System,ForCompany}()` fall back to the catalog's declared default when no row exists yet — a setting works immediately, with no seeder required. `set{System,ForCompany}()` uses `updateOrCreate()` rather than relying on a DB-level unique constraint, because MySQL allows multiple `NULL`s under a composite unique index (`(company_id, key)` wouldn't actually prevent two system-wide rows for the same key).

The global `setting(string $key)` helper (`app/Core/helpers.php`, autoloaded via composer.json's `autoload.files`) reads a **company** setting for whichever company is in `CompanyContext` — for Blade views/controllers that just want "this company's value" without resolving `SettingsService` themselves. With no company in context (e.g. a SaaS-owner request), it returns the catalog default rather than throwing.

Every catalog entry has a real, current consumer — nothing was added speculatively:

| Setting | Scope | Consumer |
|---|---|---|
| `default_trial_days` | system | `CompanyService::create()` — replaces what used to be a hardcoded `addDays(14)` |
| `default_currency_code` | system | `CompanyService::create()` — applied when no `currency_code` is given |
| `date_format` | company | Companies/Users index & show views — replaces hardcoded `->format('M j, Y')` calls |

Authorization (`SettingsPolicy`) isn't a model policy — the settings pages aren't authorized against a specific row — so its four methods are registered as named Gate abilities (`Gate::define('settings.view-company', ...)` etc.) rather than via `Gate::policy()`. Company settings follow the same "SaaS-owner staff do NOT bypass" pattern as `RolePolicy` (§3b) — a company's settings only make sense within that one company. System settings are the reverse: gated purely on `isSaasOwner()`, no Spatie permission involved (provisioning trial length/default currency platform-wide is inherently a platform-level action, same reasoning as `CompanyPolicy`).

New `settings.view`/`settings.update` permissions were added to the Module 3 catalog. Since companies created *before* this module existed already had their `Admin` role synced with whatever permissions existed at the time, `PermissionSeeder` now also re-syncs every existing company's `Admin` role with the full current permission set on every run (no-op for brand-new companies, whose `Admin` role is already complete) — the mechanism that keeps pre-existing companies from being silently locked out of a new module's permissions. Re-run `php artisan db:seed --class="App\Modules\Users\Database\Seeders\PermissionSeeder"` after deploying any module that adds new permissions.

## 3d. Audit Logs (`app/Modules/AuditLogs`) — built in Module 5

Wraps Spatie Activitylog. Its `activity_log` table has no tenant column of its own, so `config('activitylog.activity_model')` points at `App\Modules\AuditLogs\Models\ActivityLogEntry`, a subclass that adds one: a `company_id` column (migration owned by this module, since it alters a package-published table) auto-stamped in a `creating` hook.

That auto-stamp derives `company_id` from **the subject being logged, not the acting user** — a SaaS-owner editing a specific company's data must still show up in that company's own audit log, not vanish into a "system-wide" bucket just because the SaaS owner has no company of their own. Concretely: if the subject *is* a `Company`, use its own id; else if the subject has a `company_id` column, use that (correctly, including when it's genuinely `null` — a SaaS-owner `User`); else fall back to `CompanyContext::id()`. Two non-obvious bits made this fiddlier than it sounds, both caught by tests before they became real bugs:

- **`isset()` vs `array_key_exists()`**: a subject whose `company_id` genuinely *is* `null` makes `isset($subject->company_id)` report `false` (PHP's defined behavior), wrongly falling through to the `CompanyContext` branch. `array_key_exists('company_id', $subject->getAttributes())` is required instead.
- **Stale in-memory attributes**: a freshly created model's attributes only include what was explicitly passed to `create()` — an omitted `company_id` (the normal case for a SaaS-owner `User`, whose factory doesn't set one) is **absent from `getAttributes()` entirely**, not merely `null`, so even the `array_key_exists()` check above is unreliable against the cached relation Spatie hands back. `$subject->fresh()` (a real re-query) is required first.

`Company` and `User` both use `LogsActivity` with an explicit `logOnly([...])` allowlist (never a blocklist) — `User`'s excludes `password`/`remember_token` by construction, not by remembering to exclude them. `logOnlyDirty()` + `dontSubmitEmptyLogs()` keep no-op saves from generating empty log rows.

Authorization (`AuditLogPolicy`) is the opposite of `RolePolicy`/`SettingsPolicy`'s "SaaS-owner staff don't bypass" pattern: audit logs are read-only oversight, so cross-company visibility for the SaaS owner is a legitimate, intentional feature, not a gap. A company user needs `audit-logs.view` (auto-granted to `Staff` roles going forward, via the existing `%.view%` catalog-naming convention) and only ever sees their own company's entries.

## 3e. Dashboard (`app/Modules/Dashboard`) — built in Module 6

The last Phase A module, and a different kind of build from the previous five: no new domain data, just a real surface over what Modules 2–5 already produced. `/dashboard` (previously a placeholder closure in the root `routes/web.php`, added in Module 2) now belongs entirely to this module; the placeholder `resources/views/home.blade.php` was deleted.

**KPIs are two different views, not one generic one** — `DashboardController::index()` branches on `$user->isSaasOwner()` and queries accordingly, since a platform-wide view and a single-company view have almost nothing in common:

| Viewer | KPI cards | Charts | Activity feed |
|---|---|---|---|
| SaaS owner | Total/active/trial companies, total users | New companies per day (14-day line chart), companies by status (doughnut) | Across every company, with a Company column |
| Company user | Total users in their company, trial days remaining (if on trial) | Users by role (doughnut) | Their own company only |

The "users by role" and "companies by status" breakdowns both go straight at the underlying tables (`DB::table('model_has_roles')->join('roles', ...)`, a plain `groupBy('status')`) rather than through Spatie's `Role` query builder — consistent with the Module-3/5 finding that `Role`'s automatic team-scope only covers `create()`/`findOrCreate()`, so a manual aggregate query needs the tenant filter (`company_id`) explicit anyway, and going straight to the pivot table is simpler than fighting the ORM for a `GROUP BY`.

Added `<x-kpi-card>` (`resources/views/components/kpi-card.blade.php`) as the first entry in the shared Blade component library ARCHITECTURE.md §8 called for. Chart.js (installed since Module 2, unused until now) is registered globally in `app.js` (`window.Chart`); ApexCharts remains uninstalled-in-practice until a Reports/financial module actually needs it, per the original §8 split.

**Command palette (Ctrl+K)** — the other §8 UI/UX item this module closes out. `SearchController::search()` backs it: a plain `GET /search?q=`, authorized by **reusing** `CompanyPolicy`/`UserPolicy`'s existing `viewAny` checks rather than inventing new search-specific authorization — a result group is omitted entirely if the viewer can't otherwise list that resource, and a company user's user-search is scoped to their own company the same way the Users index page already is. The modal markup lives once in `resources/views/layouts/app.blade.php` (guarded by `@auth`, since search requires a logged-in user) so Ctrl+K works from every authenticated page, not just the dashboard.

## 4. Service / Repository Pattern (applied uniformly per module)

```
Controller (thin) -> Form Request (validation) -> Service (business logic, transactions, events)
    -> Repository Interface (bound in module ServiceProvider) -> Eloquent Repository
```

Every module ships `{Module}RepositoryInterface` + `Eloquent{Module}Repository`, bound in that module's provider. Controllers never call `Http::` or an external SDK directly — only through the `Support/*` manager classes (Section 5).

## 5. Pluggable Integration Frameworks

One shape, reused for Payments/SMS/Maps/AI:

```php
interface PaymentGatewayInterface {
    public function charge(PaymentRequest $request): PaymentResult;
    public function verify(string $reference): PaymentResult;
    public function refund(string $reference, ?int $amount): RefundResult;
    public function handleWebhook(Request $request): WebhookResult;
}
```

- A `*Manager` (Laravel Manager pattern) resolves the active driver **per company** from the `integrations` table's `provider` column, not a static config file.
- Adding a new provider is one driver class + one `integrations` row — zero changes to services, controllers, or domain code.
- Storage uses Laravel's native `Storage::disk()` abstraction (no custom interface needed); Email uses native named mailers.
- All credentials are stored via `integrations.credentials` with an `encrypted` cast.

### 5a. Integrations Center (`app/Modules/Integrations`) — built in Module 7

The `integrations` table + encrypted-credential CRUD + hub UI this section describes, built ahead of any actual driver. `*Manager`/`PaymentGatewayInterface`-style classes (Modules 8–11: Storage, Email, SMS, Payment) are what will actually *use* this data to make a real API call — Module 7 only has to get the storage, the form, and the extensibility contract right.

**One generic form for every provider**, not a schema per provider: the master prompt's own field list (Enable/Disable, Sandbox/Production, API Key, API Secret, Merchant ID, Username, Password, Webhook URL, Callback URL, Test Connection, Save) is uniform across every gateway/SMS/email/storage/map/AI provider, so `config('integrations.types')` only needs to declare which providers exist per type (`payment.stripe`, `sms.twilio`, …) — no per-provider field metadata. Blank credential fields on save mean "leave unchanged" (the form never re-displays a decrypted secret to type over); `IntegrationService::save()` merges onto the existing `credentials` array rather than replacing it wholesale.

**"Test Connection" is honest, not faked.** `App\Modules\Integrations\Contracts\IntegrationTester` is the contract a real driver implements; `config('integrations.testers')` maps a provider key to its tester class and starts **empty** — Module 7 registers none. Until a module registers one, clicking Test Connection sets `status = 'untested'` and reports plainly that no tester exists yet for that provider, rather than pretending to validate credentials against an API that isn't wired up. Each Phase B module adds its own tester(s) as it lands.

Authorization (`IntegrationPolicy`) follows the `RolePolicy`/`SettingsPolicy` pattern — SaaS-owner staff do not bypass, since an integration only makes sense within one specific company. New `integrations.view`/`integrations.update` permissions were added to the catalog (picked up automatically by every existing company's `Admin` role via `PermissionSeeder`'s resync, same mechanism as Module 4).

Routes are shaped `/integrations/{type}/{provider}`, not a per-row id — the controller always resolves via `(company_id, type, provider)`, so there's no numeric/UUID id a company admin could guess to reach another company's row even before the policy check runs.

### 5b. Storage (`app/Modules/Storage`) — built in Module 8

The first Phase B module to actually consume the Integrations Center rather than just build it. No controllers/views of its own — it's pure plumbing, registered purely by dropping `Providers/StorageServiceProvider.php` in place (module auto-discovery needs nothing more; see §3).

**`App\Modules\Storage\Services\StorageResolver`** decides which Laravel filesystem disk a company's files go to. `diskFor(Company $company)` looks up that company's active `type = 'storage'` integration row: no row, or the `local` provider, returns the stock `'public'` disk (works out of the box, zero config); `s3`/`r2`/`spaces` (all S3-compatible via Laravel's built-in `s3` driver — `league/flysystem-aws-s3-v3` installed for this) get their stored credentials assembled into a disk config registered at `config('filesystems.disks.company')` via `Config::set()` and returned under the fixed name `'company'`. `gcs` has no driver wired up yet and throws a clear `RuntimeException` rather than silently falling back — silently writing a company's files to the wrong disk is a correctness/compliance problem, not something to paper over the way "no tester yet" is in §5a.

A **fixed disk name** (`'company'`, not one keyed by company id) is deliberate and safe: only one company is ever in scope per request (`CompanyContext`), and this app targets non-persistent PHP workers (shared hosting, no Octane/Swoole) where `Config::set()` never survives past the request that made it — the pattern that would leak credentials between tenants under a persistent-worker runtime (Octane) is a non-issue here.

**Field remapping, not new columns.** Module 7's five generic credential fields (`api_key`/`api_secret`/`merchant_id`/`username`/`password`) don't semantically match "bucket"/"region"/"endpoint" — rather than add storage-specific columns, `config('integrations.types.storage.field_labels')` relabels the *same* fields for the storage type's edit form only (Access Key ID / Secret Access Key / Bucket Name / Region / Custom Endpoint), and `IntegrationController` merges that over the generic labels used by every other type. `providers_without_credentials` (just `local` today) hides the credentials/URLs cards entirely for a provider that needs none — this is a general Integrations Center mechanism, not Storage-specific, available to any future type/provider with the same shape.

**Real testers, registered honestly.** `LocalStorageTester` writes and deletes a small file on the `public` disk — proves the disk is actually writable, the realistic shared-hosting failure mode (permissions), not a credentials problem. `S3CompatibleTester` (shared by `s3`/`r2`/`spaces`) calls `StorageResolver::diskForIntegration()` — a variant of `diskFor()` that builds a disk from *this* integration's credentials regardless of its `is_active` flag, so a provider can be verified before being switched on — then does the same write/delete round-trip against the real bucket. Both registered in `config('integrations.testers')`; `gcs` is deliberately left unregistered, so it correctly falls through to §5a's honest "no tester yet" message.

**`companies.storage_disk` (Module 2) is dropped**, not deprecated-in-place. It was speculative scaffolding for "which disk" before this module existed to answer that; now that the real answer needs credentials, not just a disk name, the `integrations` table (Module 7) is strictly more capable and the bare column would just be dead, confusing data. `CompanyService::updateBranding()` now calls `StorageResolver::diskFor($company)` and passes the result to Spatie Media Library's `toMediaCollection('logo', $disk)` — the first real proof the wiring works end to end; `CompanyController::updateBranding()` catches the `RuntimeException` for an unimplemented provider and flashes it as a normal form error instead of a 500.

### 5c. Email (`app/Modules/Email`) — built in Module 9

Same shape as Storage (§5b): no controllers/views, just `Providers/EmailServiceProvider.php` for module discovery, consumed entirely through the Integrations Center's `config('integrations.testers')`.

**One transport for every provider, deliberately.** `smtp`/`gmail`/`microsoft365`/`mailgun`/`sendgrid`/`ses` are all reachable over plain SMTP (Gmail/365 app passwords, Mailgun/SendGrid/SES-issued SMTP credentials), so `App\Modules\Email\Services\EmailResolver` needs exactly one transport (`smtp`, built into Laravel, no extra composer package) instead of `aws/aws-sdk-php` for SES or `symfony/mailgun-mailer` for Mailgun — consistent with the project's shared-hosting-lean bias toward fewer dependencies. `mailerFor(Company $company)` reads the company's active `type = 'email'` integration; no row falls back to `config('mail.default')` (whatever `.env` sets — `log` locally). `mailerForIntegration()` (used directly by Test Connection, ignoring `is_active`, same reasoning as `StorageResolver::diskForIntegration()`) registers a `Config::set('mail.mailers.company', ...)` entry and returns `'company'`.

Reuses Module 8's generic `field_labels` mechanism (type-level, no new config shape needed): the same five credential fields are relabeled Host / Port / Encryption / Username / Password for the whole `email` type. Five preset providers (everything except plain `smtp`) get well-known host/port/encryption defaults baked into `EmailResolver::PRESETS` so only Username/Password are strictly required — but Host stays editable and overrides the preset when filled in (e.g. Mailgun's EU region uses a different host).

**"Test Connection" sends a real email**, not a throwaway file write like Storage's testers — there's no cheaper way to prove SMTP credentials actually work. `SmtpEmailTester` (one class, registered for all six providers) sends to whoever clicked the button (`Auth::user()->email`, falling back to the company's own contact email), so the result lands in an inbox they can check immediately. Verified live: a real SMTP connection attempt against an unroutable host failed with a genuine transport-level error message, surfaced cleanly rather than crashing.

### 5d. SMS (`app/Modules/Sms`) — built in Module 10

Unlike Storage/Email, **no shared native transport exists for SMS** — every provider is a genuinely different HTTP API, so this is the first module to build the actual `*ProviderInterface` + `*Manager` pattern described in §5, rather than lean on something Laravel already ships.

`App\Modules\Sms\Contracts\SmsProviderInterface` is the uniform seam (`send(Integration $integration, string $to, string $message): array{success, message, message_id?}`). Each of the six catalog providers gets its own driver in `App\Modules\Sms\Drivers`, implementing that interface *and* (for five of the six) `IntegrationTester`, so the same class is both the real send capability and the Test Connection check — no separate resolver layer needed the way Storage/Email have one, since drivers already read credentials directly off the `Integration` they're given.

`App\Modules\Sms\Services\SmsManager::send(Company $company, string $to, string $message)` resolves a company's active `type = 'sms'` integration and delegates to its driver (looked up via `config('integrations.sms_drivers')`, a complete 6-provider map — separate from `config('integrations.testers')`, which only lists the five drivers confident enough to double as a credential-verification check; see below). No active integration, or an unregistered driver, returns a failure result rather than throwing — a future caller (Notifications, Module 12) branches on the result the same way it would branch on a rejected send.

**Field mapping is genuinely different per provider** (unlike Storage/Email, where one type-level relabeling fit every provider), because each gateway's real API expects different things: Twilio needs Account SID/Auth Token/From number; Infobip needs an API key, a Sender, and an *account-specific base URL* (mapped onto the otherwise-unused `username` field); ClickSend and Africa's Talking both authenticate with a username-shaped credential *and* a secret, just swapped which of `api_key`/`api_secret` holds which. Each driver's class docblock documents its exact mapping; the Integrations Center form itself stays the one generic 5-field layout (§5a), just with type-level labels honest enough to cover all six (`API Key / Account SID / Username`, etc.) rather than claiming a precision the shared form can't deliver.

**Confidence is documented per provider, not assumed uniform.** Twilio, Infobip, ClickSend, and Africa's Talking are built against long-stable, extensively-referenced public REST APIs. Beem (a regional East African gateway) is implemented to the best of publicly available documentation but flagged in its own docblock as unverified against a live account. **NextSMS** — the least publicly documented provider in the catalog — implements `SmsProviderInterface` for `send()` but deliberately does **not** implement `IntegrationTester`: there's no credential-check endpoint confident enough to present as real verification, so it has no entry in `config('integrations.testers')` and Test Connection honestly falls through to §5a's "no tester yet" message rather than faking one. This is the same honesty principle as GCS in §5b, applied to a case where even the *send* behavior — not just a nice-to-have balance check — carries a documented confidence caveat.

**No live smoke test against a real provider.** Every other Phase B module (Storage, Email) was verified with a real network call — a real S3-shaped request, a real SMTP connection attempt — because those cost nothing and needed no third party's consent. Sending a real SMS costs real money against real credits and reaches a real phone number; without real credentials or explicit authorization to spend on them, no live send or credential-check was attempted against any actual provider. Verified instead: all 28 tests use `Http::fake()` (zero real network egress, enforced in every driver test), plus a database-only check that `integrations.credentials` round-trips encrypted for `type = 'sms'` rows exactly like every other type.

### 5e. Payments (`app/Modules/Payments`) — built in Module 11

Same shape as SMS (§5d): `App\Modules\Payments\Contracts\PaymentGatewayInterface` is the uniform seam (`charge`/`verify`/`refund`, all returning `array{success, message, ...}` — never a float for money, always integer minor units/cents, to avoid the rounding bugs float-based money handling invites), `App\Modules\Payments\Services\PaymentManager` resolves a company's active `type = 'payment'` integration and delegates to its driver via `config('integrations.payment_drivers')` (all twelve catalog providers, every one a real driver). `charge()` uses whichever gateway is currently active (the only sensible default for a *new* charge); `verify()`/`refund()` instead take an explicit provider, since they act on a transaction that was already charged through a *specific* gateway — one the company might have since switched off.

**All twelve catalog providers have a real driver — confidence, not implementation, is what varies.** Initially the nine non-Stripe/PayPal/Flutterwave providers shipped as a single honest "not implemented" stub; per explicit direction, every provider now has a genuine, working implementation instead, so the only thing standing between any of them and moving real money is a real merchant account's credentials (and, for five of them, a confirmed API host — see below). Each driver's own docblock states its confidence tier plainly:

- **High** — Stripe, PayPal, Flutterwave: built against stable, extensively-referenced public REST APIs with simple Bearer-token or Basic-Auth-then-Bearer authentication.
- **Moderate** — Selcom (HMAC-SHA256 request signing, canonicalization reconstructed from Selcom's circulated Vendor API docs — the exact digest string may need adjusting against a live account; isolated in one `buildDigest()` method so that's a one-place fix), M-Pesa (Safaricom's Daraja API pattern, the most standardized mobile-money shape in the region), Airtel Money (Airtel Africa's published Open API), AzamPay (a real but less globally-referenced aggregator).
- **Low, base URL required** — Tigo Pesa, HaloPesa, NMB, CRDB, NBC: this app has no confirmed public hostname for any of these five. Rather than guess at one (a fabricated host would just fail to resolve, "waiting on credentials" in name only), each driver's request/response handling is fully real and reads its base URL from the credential form's Password field ("Base URL Override") — the moment a real integration agreement supplies one, these are as ready as any other provider, no code change required.

Every driver implements `IntegrationTester` too (all twelve are registered in `config('integrations.testers')`) — Storage's GCS (§5b) is now the *only* provider left in the entire catalog without one, since Maps/AI (Phase E) haven't been built yet.

**`refund()` is honest about what each gateway actually supports**, not uniform for uniformity's sake: Stripe/PayPal/Flutterwave/M-Pesa (Daraja's Transaction Reversal API)/Airtel Money (a published refund endpoint) genuinely support it and call a real endpoint; Selcom, AzamPay, Tigo Pesa, HaloPesa, NMB, CRDB, and NBC do not expose a self-service refund/reversal API to merchants in practice (mobile money reversals and bank collection reversals both typically go through a support/dispute process, not a public endpoint) — those seven honestly report that and make no API call, rather than fabricating an endpoint with no real backing.

**`charge()`'s realistic shape for card gateways is a hosted redirect, not an inline charge.** Stripe's driver creates a Checkout Session; PayPal's creates an Order and returns its approval link. Neither app has a Stripe.js/PayPal-JS frontend integration yet (no Tenant Portal exists until Phase E), so a fully server-side "instant" charge without a saved payment method isn't a real capability to claim — a hosted checkout redirect is the correct, honest thing an unauthenticated backend integration can actually do today. The mobile-money/bank drivers instead prompt the customer's phone directly (an STK-push-style collection request) — no redirect needed, the customer approves on-device. All three card gateways carry real idempotency wiring per the provider's own mechanism (Stripe's `Idempotency-Key` header, PayPal's `PayPal-Request-Id` header, Flutterwave's `tx_ref` field) — the caller-supplied `$reference` becomes that key, so a retried charge can't double-charge, directly satisfying §6's "SMS/payment jobs get idempotency keys" requirement.

**No live smoke test against a real gateway**, for the same reason as SMS (§5d) plus a materially higher one: real money. All 73 tests run against `Http::fake()` (zero real network egress, enforced across every driver including the five "no base URL configured" failure paths); verified instead via a database-only check that `integrations.credentials` round-trips encrypted for `type = 'payment'` rows and that every one of the twelve catalog providers resolves to its correct driver class.

### 5f. Notifications (`app/Modules/Notifications`) — built in Module 12

The module that finally gives Storage/Email/SMS a real business consumer, closing out Phase B. In-app notifications use Laravel's own `notifications` table/`Notifiable` trait as-is (no custom model, no added `company_id` column the way Module 5's `activity_log` got one — a notification is inherently per-user, and there's no concrete cross-company "notification log" screen in scope to justify one; add it only if one is ever actually needed).

**Two custom notification channels route through this app's own resolvers instead of Laravel's defaults**: `App\Modules\Notifications\Channels\CompanyMailChannel` sends via the recipient's own company's configured mailer (`EmailResolver::mailerFor()`, falling back to `config('mail.default')` for a notifiable with no company — i.e. SaaS-owner staff); `CompanySmsChannel` sends via the recipient's company's configured SMS gateway (`SmsManager::send()`), silently doing nothing if the notifiable has no phone number — added `users.phone` (nullable) specifically as this channel's destination, the first real consumer for it. Both are registered against their custom channel names (`'company-mail'`, `'company-sms'`) via `Notification::extend()` in `NotificationsServiceProvider::boot()`, not left to Laravel's naming-convention auto-resolution. A notification opts in per-channel: `toCompanyMail($notifiable): array{subject, body}` / `toCompanySms($notifiable): string`, mirroring `toMail()`/`toArray()`'s existing shape.

**First real trigger: `TrialEndingSoon`**, chosen because `companies.trial_ends_at` has existed since Module 2 and needs no Phase C domain data to be meaningful. `App\Modules\Notifications\Console\Commands\NotifyTrialsEndingSoon` (the app's first scheduled command — see §6) finds companies whose trial ends in *exactly* 3 days (not a rolling "within N days" window, which would re-notify daily) and notifies each company's Admin-role users (resolved via the same direct `model_has_roles`/`roles` table join Module 6's Dashboard uses, not Spatie's `Role` query builder — see the teams caveat in §1) via `database` + `company-mail` only, deliberately not `company-sms`: a trial reminder is informational, not urgent enough to justify spending real SMS credit on every admin of every trialing company. Idempotent by construction — it checks for an existing `TrialEndingSoon` notification with the same `company_id`/`trial_ends_at` in the `data` JSON column before sending, so re-running the command (or a slow cron catching up) never double-notifies.

**UI**: a topbar bell (badge count fetched once per page load; the dropdown's actual list is lazy-loaded only when clicked, never polled — this app targets shared hosting with no WebSockets/push) plus a full `/notifications` index page with mark-read/mark-all-read, matching the list-page conventions established since Module 2. Every authenticated user gets one (`@auth`-gated, not permission-gated) — notifications are inherently personal, same reasoning as the command palette.

## 6. Queue & Scheduling on Shared Hosting

Single cron entry: `* * * * * php /path/artisan schedule:run >> /dev/null 2>&1`. The Laravel Scheduler drives `queue:work --stop-when-empty` plus periodic business-rule commands. **`notifications:trial-ending`** (Module 12) is the first real one, scheduled `->daily()` — registered from `NotificationsServiceProvider::boot()` via `$this->app->booted(fn () => ...)` rather than editing `routes/console.php`, so the module stays self-contained per §1's "adding a module needs zero core-file changes" rule. Failed jobs land in `failed_jobs` with `tries`/`backoff` per Job class; SMS/payment jobs carry idempotency keys.

## 7. Security

Spatie Permission with the **teams** feature (`team_foreign_key` = `company_id`) — wired in Module 3. A `Policy` per module model, consulted via `authorize()`, combining a permission check with an explicit same-company comparison (permissions never cross the tenant boundary). `IdentifyCompany` + the `BelongsToCompany` global scope give defense in depth against cross-tenant leakage for our own models; Spatie's `Role`/`Permission` models have no such automatic scope (see the teams caveat in §1), so policies are the sole enforcement point there. Rate limiting on auth/OTP/webhook endpoints. Uploads via Spatie Media Library with MIME/size limits. Integration secrets encrypted at rest (Section 5).

## 8. UI/UX System

Bootstrap 5 with CSS-variable theming for light/dark (no separate dark stylesheet). Shared Blade component library, grown incrementally as modules need pieces of it (`<x-kpi-card>` landed in Module 6; data-table/empty-state/skeleton patterns exist inline in module views today and get extracted into components if/when a second module needs the exact same markup — not preemptively). Command palette (Ctrl+K, Module 6) in vanilla JS against `GET /search`. Chart.js for dashboard KPIs (wired in Module 6); ApexCharts stays installed-but-unused until a financial/reporting module needs it.

**Note on list pages: server-side pagination, not DataTables.** `datatables.net-bs5` is an installed dependency and registered globally (`window.DataTable` in `resources/js/app.js`), but every list view (Companies/Users/Roles) actually uses Laravel's own paginator with a server-side search form — the correct choice for "scale to millions of records" (§1), since DataTables' client-side sorting/searching only operates on whatever page of data already got fetched. DataTables stays installed-but-unused, the same "not preemptive" stance as ApexCharts above, in case a future list genuinely needs client-side table interaction over a small, fully-loaded dataset.

**Design system (post-Module-11 pass):** a Stripe/Linear-inspired clean/minimal direction, applied entirely through Bootstrap 5's own SCSS variable overrides in `resources/css/app.scss` (no parallel CSS framework, no `!important` fighting) — self-hosted Inter font (`@fontsource/inter`, latin-only subset to keep the shared-hosting build lean), a restrained indigo primary color, a softer shadow/radius scale replacing heavy borders, tightened heading letter-spacing, a sticky/blurred topbar, soft-pill sidebar active states, card hover-lift, refined form focus rings, and a `prefers-reduced-motion`-respecting content fade-in. Every value rides Bootstrap's own CSS custom properties, so `data-bs-theme="dark"` continues to reskin the whole app with zero extra dark-mode rules. SweetAlert2 confirmation dialogs are consolidated into one `window.confirmDelete(name, form, text)` helper (`resources/js/app.js`) instead of each view repeating its own `Swal.fire()` block — it's dark-mode-aware (SweetAlert2 doesn't read `data-bs-theme` on its own) and defaults to an accurate "This action cannot be undone" for hard-deleted models, with an explicit soft-delete-specific message passed via `data-text` only where that's actually true (`Company` — the one model in the app using `SoftDeletes` so far).

## 10. Core Real Estate Domain

### 10a. Properties, Buildings & Units (`app/Modules/Properties`) — built in Module 13

The first Phase C module, and the first genuinely hierarchical domain module: a company's `Property` has many `Building`s, each with many `Unit`s (`Property hasMany Building hasMany Unit`, plus a `Property hasManyThrough Unit` for direct counts/queries). All three follow the same conventions as every tenant-owned table since Module 2 (`BelongsToCompany`, `HasUuid`, `SoftDeletes`) — `company_id` is denormalized onto `buildings`/`units` too (not just `properties`), matching the established indexing convention, even though it's derivable through the parent chain.

**One permission group governs the whole hierarchy**, not three independently-permissioned ones: `properties.viewAny`/`view`/`create`/`update`/`delete` cover Property, Building, *and* Unit management. Buildings and units are always managed in the context of managing properties — there's no real-world case for "can edit properties but not the buildings inside them" — so splitting into `buildings.*`/`units.*` permission groups would be permission-explosion without a matching real need. `PropertyPolicy`/`BuildingPolicy`/`UnitPolicy` follow the same no-SaaS-owner-bypass pattern as `RolePolicy`/`SettingsPolicy`/`IntegrationPolicy` (§3b/§3c/§5a) — a property is operational business data belonging to exactly one company, not something the SaaS owner administers directly the way Companies/Users are. `BuildingPolicy::create()`/`UnitPolicy::create()` take the *parent* (`Property`/`Building`) as their second argument, since the child doesn't exist yet to check against — called via `authorize('create', [Building::class, $property])`.

**Routes are shallow-nested**: `properties/{property}/buildings/create` and `.../buildings` (POST) need the parent in the URL to know what they're attached to, but `buildings/{building}` (show/edit/update/destroy) stand alone once a building exists — the same pattern one level down for units under buildings. The web UI doesn't have separate Buildings/Units index pages; a property's buildings are listed inline on its own show page, and a building's units inline on its show page — building/unit lists are always viewed in their parent's context in practice, so a standalone index would just be a redundant, differently-scoped view of the same data. The API mirrors this shape but does add index endpoints (`GET properties/{property}/buildings`, `GET buildings/{building}/units`) — a headless client legitimately might want to list a parent's children directly without the same "always shown inline" web-UI constraint.

**Money stored as `DECIMAL(12,2)`, not integer minor units.** `units.rent_amount` uses ordinary decimal storage (MySQL's `DECIMAL` is exact, not floating-point, so there's no precision-drift risk) rather than the integer-cents convention `App\Modules\Payments\Contracts\PaymentGatewayInterface` requires (§5e). That convention exists specifically for third-party gateway API payloads, not this app's own domain storage — Rent Collection (Module 18), when it actually calls `PaymentManager::charge()`, is where the decimal-to-minor-unit conversion belongs, at the integration boundary, not here.

**`Property` gets a `photos` media collection** (Spatie Media Library, multi-file — unlike `Company`'s single-file `logo`), the first multi-photo gallery in the app. `latitude`/`longitude` are stored now (plain nullable decimals) even though no map is rendered yet (Maps framework is Phase E, §5's Support layer) — storing a location is just data, the same way `Company` stores an address without any mapping feature; rendering it is a separate, later concern.

**Dashboard KPIs got a real new consumer**: a company's dashboard (§3e) now shows Properties/Units counts and an occupancy rate (`occupied ÷ total`, `null` — not `0%` — when a company has no units yet, so the KPI card can be hidden rather than showing a misleading "0%"). The SaaS-owner dashboard was deliberately left untouched — properties aren't something the SaaS owner administers (see the policy note above), so aggregating them into the platform-wide view would cut across that same boundary.

**Testing note**: a route bound to a model outside the acting user's company (denied by `BelongsToCompany`'s global scope + an explicit policy check) resolves correctly and returns 403 on the *first* request within a test, but can 404 on a *second*, identical in-process request to the same cross-company URL within the same PHPUnit test method — reproduced and isolated down to "any second request to a cross-company-scoped bound route within one test process," unrelated to GET vs. POST. Both outcomes correctly deny access either way, and every real HTTP request in production boots a fresh PHP process (no shared state to trigger this), so it's a test-harness-only artifact, not a production concern — the fix is simply one HTTP-layer assertion per test method for this shape of route, which the rest of the codebase already did by convention before this was ever diagnosed.

### 10b. Landlords (`app/Modules/Landlords`) — built in Module 14

Adds the property-owner side of the domain: `Landlord hasMany Property`, and `properties.landlord_id` (nullable FK, `nullOnDelete`) — deliberately **deferred from Module 13** until this module existed to answer "which landlord," the same discipline Module 3 applied adding `company_id`/`uuid` to the pre-existing `users` table rather than speculatively scaffolding a foreign key to a table that didn't exist yet. One property → one landlord for now (no co-ownership/percentage-split modeling) — a real simplification, not an oversight; add multi-owner support if a real need for it shows up, not ahead of one.

**`LandlordPolicy` follows `PropertyPolicy`'s no-SaaS-owner-bypass pattern** (§10a) — a landlord record, including its bank details, is single-company operational data. Landlord management gets its **own** `landlords.*` permission group, separate from `properties.*` — unlike Buildings/Units (governed by the same permission as their parent Property, since they're never managed independently), a landlord record holds sensitive financial data (bank details, tax ID) that not every property-editing user necessarily needs access to, so it's a genuinely separate concern warranting its own permission boundary. *Assigning* an existing landlord to a property is still just part of `properties.update` (a dropdown selection, not landlord management) — the property edit form doesn't gate the dropdown's *options* behind a second `landlords.view` check, only whatever already gates the form itself.

**Bank details are encrypted at rest but *not* masked in the UI — a deliberate contrast with `integrations.credentials` (§5a).** Integration credentials are write-only third-party secrets Module 7 never re-displays, only re-enters. A landlord's bank details are the *company's own* reference data about its landlord — a company admin legitimately needs to see the full account number to actually process a bank transfer. So `landlords.bank_details` uses the same `encrypted:array` cast (protecting against DB-level exposure — backup theft, an SQL dump, etc.) but the edit form and API response both show it in full, not masked. The form collects it as five individual `bank_*` inputs (`bank_name`/`bank_account_name`/`bank_account_number`/`bank_branch`/`bank_swift_code`); `LandlordService::create()`/`update()` assemble them into the single `bank_details` array the model's cast expects — this assembly lives in the **service layer**, not either controller, so the web and API controllers (which both need identical behavior) don't duplicate it.

**`tax_id` is deliberately *not* encrypted**, unlike `bank_details` — it's needed for search/reporting in a way encryption would block, and is lower-sensitivity than a bank account number; a judgment call, not an oversight.

**Real new consumers wired into Module 13's existing surfaces**, not just a standalone CRUD screen: the Property create/edit form gained a landlord dropdown (scoped to the acting user's own company - `Rule::exists('landlords','id')->where('company_id', ...)` blocks cross-company assignment at validation time, since the bare foreign key itself doesn't know about tenancy), the properties index/show pages display the assigned landlord, and `PropertyResource` includes it via `whenLoaded`. A landlord's own show page lists their properties (with building counts) the same way a property's show page lists its buildings (§10a's established "children shown inline on the parent's page" pattern).

**`LandlordSeeder` runs after `PropertySeeder`** in `DatabaseSeeder` (2-4 landlords per company, with bank details, assigned to roughly 70% of that company's existing properties — the other 30% deliberately left unassigned, since "no landlord yet" is a normal state, not an error condition) — realistic hierarchical sample data across Properties → Landlords for local dev.

### 10c. Tenants (`app/Modules/Tenants`) — built in Module 15

Adds the occupant side of the domain, alongside Landlords rather than nested under Properties. `Tenant` gets its **own** `tenants.*` permission group, for the same reason `landlords.*` is separate from `properties.*` (§10b): tenant screening data (identification, blacklist status, emergency contacts) is sensitive enough to warrant its own permission boundary rather than riding on `properties.update`. `TenantPolicy` follows the established no-SaaS-owner-bypass pattern — tenant records are single-company operational data, not something the SaaS owner administers.

**`identification_number` is encrypted at rest but *not* masked in the UI — the same reasoning as Landlord's `bank_details` (§10b), not a repeat of the Integration-credentials pattern.** It's the company's own reference data about a person they've screened and are (or were) leasing to; a company admin needs to see the full ID number to verify it against a physical document. Unlike `bank_details`, this is a single scalar value, not a structured set of sub-fields, so it uses the plain `encrypted` cast rather than `encrypted:array` — no service-layer assembly step is needed the way Landlord's five `bank_*` inputs required one.

**`status` includes a real `blacklisted` value** (alongside `active`/`inactive`) — a genuine tenant-screening feature, not a soft-delete substitute. A blacklisted tenant is still a full record a company wants to keep and search (to recognize the same person applying again under a new lease elsewhere in their portfolio), which is exactly why it's a status value rather than being expressed via `deleted_at`. The tenant's show page renders a prominent red warning banner when `isBlacklisted()` is true, so front-desk staff can't miss it.

**Deliberately no `Property`/`Unit` link yet.** Unlike Landlord → Property (added the moment Landlords existed, since a property needs to know its owner), a Tenant only becomes associated with a specific unit through a lease, and Lease Management doesn't exist yet — inventing a `tenants.unit_id` column now would mean modeling occupancy without the lease terms (start/end date, rent amount, deposit) that actually govern it. This is the same deferred-FK discipline as `properties.landlord_id` (§10b) and `users.company_id` (§3), applied one module earlier in the chain this time: the column is added in Module 16 (Lease Management) once there's a real lease record to hang it off, rather than a bare FK with no context.

**`TenantSeeder` runs after `LandlordSeeder`** in `DatabaseSeeder` (4-8 active + 0-2 inactive + 0-1 blacklisted tenants per company), with no Property/Unit linkage — consistent with the point above, that linkage doesn't exist until Lease Management.

### 10d. Lease Management (`app/Modules/Leases`) — built in Module 16

Finally links Tenants to Units, the connection §10c deliberately deferred - a `Lease` `belongsTo` both `Tenant` and `Unit`, with `tenant_id`/`unit_id` using `restrictOnDelete()` (not `nullOnDelete()` like `properties.landlord_id`, §10b) since a lease's tenant/unit are essential to what the record *is* - financial and occupancy history - not an optional assignment; hard-deleting either while leases reference them fails loudly rather than silently orphaning the record. Gets its own `leases.*` permission group, following the same reasoning as `landlords.*`/`tenants.*` (§10b/§10c): lease terms (rent, deposit, dates) are sensitive operational data warranting an independent boundary. `LeasePolicy` follows the established no-SaaS-owner-bypass pattern.

**`units.status` is the single source of truth for occupancy, kept in sync by `LeaseService`, not by a separate "is there an active lease" query.** Creating a lease requires the target unit to currently be `vacant` (enforced in `StoreLeaseRequest` via a scoped `Rule::exists` closure - the same discipline as `properties.landlord_id`'s company-scoping, §10b) and immediately flips it to `occupied`; a lease leaving the `active` status (`expired` or `terminated`) flips its unit back to `vacant`, unless another active lease already accounts for it (shouldn't happen given the creation rule, but `LeaseService::syncUnitStatus()` guards the invariant regardless of entry point). This means there is deliberately no separate "is this unit occupied" query anywhere in the app - `units.status` already answers it, and Module 13's dashboard occupancy KPI (§10a) already reads it, so it picks up real lease-driven occupancy with no changes of its own.

**A subtle Eloquent trap surfaced building this**: `LeaseService::create()`'s `$attributes` never includes `status` (it's not in `StoreLeaseRequest`'s rules at all - every new lease simply starts `active`, relying on the `leases.status` column's DB default). But a column's DB default never round-trips onto the in-memory model after `save()` - Eloquent only refreshes the auto-increment key and timestamps, not other DB-computed defaults - so `$lease->status` was `null` in PHP immediately after creation even though the database correctly stored `'active'`, which silently broke `syncUnitStatus()`'s `=== 'active'` check right after every create. Fixed with Eloquent's own `protected $attributes = ['status' => 'active', 'billing_cycle' => 'monthly']` default-attribute mechanism on the `Lease` model, mirroring the migration's column defaults in PHP so the in-memory object is correct the instant it's constructed, not just after a `fresh()`.

**`tenant_id`/`unit_id` are fixed at creation - `UpdateLeaseRequest` doesn't accept either.** Changing a lease's tenant or unit isn't a real-world "edit"; it's ending one occupancy and starting another, which is exactly what creating a new lease (against a newly-vacant unit) already models. The edit form shows both as read-only. `end_date`, `billing_cycle`, `rent_amount`, `deposit_amount`, `status`, and `termination_reason` remain editable - a renewal is extending `end_date`, and ending a lease early is a `status` change to `terminated`, not a delete.

**`terminated_at` is derived, not form input** - the moment a lease's `status` actually transitions to `terminated`, set by `LeaseService::update()` itself, the same discipline as `companies.trial_ends_at` being system-set rather than user-supplied.

**A lease that simply runs out gets expired by the clock, not by a human.** `App\Modules\Leases\Console\Commands\ExpireLeases`, scheduled daily via `LeasesServiceProvider::boot()` (Module 12's `NotifyTrialsEndingSoon` precedent, §7's Notifications module), flips any `active` lease whose `end_date` has passed to `expired` through the same `LeaseService::update()` path a manual termination uses - so a lease ending via the clock frees its unit identically to one ended through the UI, with no duplicated logic.

**Real new consumers wired into Module 13's and Module 15's existing surfaces**, not a standalone island: a vacant unit's show page gains a "Start Lease" button (linking to `leases.create?unit_id=...`, which pre-selects that unit in the create form's dropdown) and an occupied unit's show page shows its current tenant and a link to the lease; a tenant's show page gains a full lease history table, the same "children shown inline on the parent's page" pattern as Landlord's Properties list (§10b) and Property's Buildings list (§10a).

**`LeaseSeeder` runs after both `PropertySeeder` and `TenantSeeder`** in `DatabaseSeeder` (it needs both), pairing roughly half of each company's vacant units with a random non-blacklisted tenant into an active lease (leaving the rest vacant - a portfolio at less than full occupancy is the normal state, the same restraint `LandlordSeeder` applies, §10b), plus a couple of historical (`expired`/`terminated`) leases on units that stay vacant post-seeding. Bypasses `LeaseService` and sets `units.status` directly, matching `LandlordSeeder`'s direct-mutation convention for seeders (§10b).

### 10e. Invoices (`app/Modules/Invoices`) — built in Module 17

Bills a `Lease`, not a `Tenant` or `Unit` directly - `Invoice belongsTo Lease`, with `lease_id` using `restrictOnDelete()` (the same reasoning as `leases.tenant_id`/`unit_id`, §10d: an invoice's lease is essential to what the record is, a financial document, not an optional assignment). Tenant/unit/property are reached through `$invoice->lease->tenant`/`$invoice->lease->unit`, not denormalized onto `invoices` - unlike `company_id` (denormalized on every tenant-owned table for tenant-scoping), there's no query-performance reason to duplicate a mid-hierarchy FK here. Gets its own `invoices.*` permission group, `InvoicePolicy` follows the established no-SaaS-owner-bypass pattern; status-changing actions (send/cancel/record a payment) are all still gated by the plain `update` permission, not one apiece - the same restraint `LeasePolicy` applies to termination (§10d).

**Three tables, not one JSON blob.** `invoices` holds the document-level fields (dates, status, denormalized `total_amount`/`amount_paid`); `invoice_items` (description/quantity/unit_price/amount) and `invoice_payments` (amount/paid_on/method/reference/`recorded_by_id`) are real child tables, not an `encrypted:array`-style column like Landlord's `bank_details` (§10b) - unlike a landlord's five bank fields, an invoice's line items and payment history are open-ended repeating structured data that a real ERP needs to query and report on individually later (Phase E reporting), which a JSON column can't do well. Both child tables get `HasUuid`/`BelongsToCompany` like every other domain table in this app, even though neither has its own route - consistent with `Building`/`Unit` having full identity despite being reached only through their parent (§10a).

**`status` is never a raw editable field - it only ever changes through an explicit service method**, unlike every other module's status column so far (`Landlord`/`Tenant`/`Lease` all just take `status` as a plain validated form field). `InvoiceService::send()`, `cancel()`, and `recordPayment()` each enforce their own legal-transition rules and are the *only* way `status` changes after creation - `StoreInvoiceRequest`/`UpdateInvoiceRequest` never accept it, and `RecordInvoicePaymentRequest` only accepts payment details. This is a deliberate stricter pattern than the rest of the app: a `paid` status is a *consequence* of recorded payments summing to the total, not an independent fact a form could assert - letting a client set `status: "paid"` directly would let `amount_paid` and `status` disagree with each other, which is exactly the kind of inconsistency a financial document can't tolerate.

**Only a `draft` invoice is editable.** `InvoiceService::update()` (and `delete()`) reject the request outright once an invoice has been sent - correcting a sent invoice means cancelling it and issuing a new one, not silently mutating a document the tenant may already have been shown, the same "no editing past a lifecycle point" discipline as Lease's fixed `tenant_id`/`unit_id` (§10d). Line items are always replaced wholesale on create/update (delete-then-recreate), never diffed - simpler than reconciling adds/removes/edits against existing rows, and `total_amount` is recalculated server-side from the submitted items every time, never trusted from the request.

**`invoice_number` is sequential per company (`INV-000001`, `INV-000002`, ...), generated from a row count, not a dedicated sequence table or a locking `SELECT ... FOR UPDATE`.** The actual correctness guarantee is the `unique(company_id, invoice_number)` database index (see the migration) - a colliding insert under real concurrent creation for the same company fails loudly instead of silently producing two invoices with the same number. This is a deliberate, documented simplification: a proper counter/lock is a reasonable upgrade if this app's write concurrency ever justifies it, not before, given the shared-hosting/low-concurrency reality the whole architecture targets (§1).

**`MarkOverdueInvoices`, scheduled daily (`InvoicesServiceProvider::boot()`, the same `ExpireLeases` precedent, §10d), does a plain bulk `UPDATE` rather than going through `InvoiceService`** - unlike `ExpireLeases`, which has to go through `LeaseService` because expiring a lease has a real side effect to keep in sync (freeing the unit), marking an invoice `overdue` has no side effect on any other model, so there's nothing a service call would add except overhead. Paying an overdue invoice afterwards still works normally through `recordPayment()` - `overdue` isn't a dead end, just an informational status.

**Real new consumers wired into Module 16's existing surfaces**: a lease's show page gained an "Invoices" section listing every invoice billed against it plus a "New Invoice" button that pre-selects that lease on the create form (via `?lease_id=...`, the same query-string-prefill pattern as Unit's "Start Lease" button, §10d) - the same "children shown inline on the parent's page" convention as Tenant's lease history (§10c) and Landlord's properties list (§10b).

**The line-item table on the create/edit form is genuinely dynamic (add/remove rows) via plain vanilla JS** (`initInvoiceLineItems()` in `resources/js/app.js`, cloning a `<template>` element) - no client-side framework, consistent with the "no Node in production" constraint (§1): Vite compiles this JS once at build time same as every other script in the app.

**`InvoiceSeeder` goes through `InvoiceService`, unlike every other seeder so far**, which mutate Eloquent directly (`LandlordSeeder`'s `landlord_id` assignment, `LeaseSeeder`'s `units.status` sync, §10b/§10d). Invoice-number generation and total computation are real business logic that a seeder shouldn't reimplement or bypass - if it did, seeded data could produce duplicate invoice numbers or totals that don't match their items, exactly the kind of inconsistency the service exists to prevent. It runs after `LeaseSeeder` (needs leases to bill), creating 1-3 months of back invoices per lease with a randomized mix of draft/sent/paid/partially_paid/overdue outcomes for realistic sample data.

## 11. Rent Collection (`app/Modules/RentCollection`) — built in Module 18

The roadmap describes this module as "consumes Payments + Invoices + SMS/Email reminders" rather than adding its own domain entity, and that's exactly its shape: it has no index/create/show screens of its own, only orchestration (an online-charge action layer on Invoice, a public webhook, two scheduled commands) plus a small amount of UI added to Invoice's and Tenant's existing pages. Gets its own top-level `## 11` heading rather than a `### 10f` under Core Real Estate Domain (§10) - unlike Properties/Landlords/Tenants/Leases/Invoices, it isn't itself a real-estate domain entity, it's the integration layer connecting two already-built subsystems (§5's Payments framework and §10e's Invoices), so it doesn't belong in the same list as the things it consumes.

**`Invoice belongsTo Lease`, and now `Invoice hasMany InvoicePaymentAttempt`** (`app/Modules/RentCollection/Models/InvoicePaymentAttempt.php`) - a genuinely new child table, not folded into `invoice_payments` (§10e), because a payment *attempt* and a confirmed *payment* are different things with different lifecycles: an attempt can be `pending`/`failed` and never become a real payment at all, while `invoice_payments` (Module 17) is reserved for money that's actually been received (manually recorded, or gateway-confirmed - see below). `InvoicePaymentAttempt.provider`/`reference`/`amount_minor`/`currency` mirror `PaymentGatewayInterface`'s own vocabulary (§5), not `invoices.total_amount`'s decimal convention - this table is the one place in the whole app, other than the drivers themselves, that speaks in integer minor units, because it's sitting directly on the integration boundary Module 13's original note about `units.rent_amount` pointed to ("Rent Collection... is where the decimal-to-minor-unit conversion belongs, at the integration boundary, not here").

**`RentCollectionService::chargeInvoice()` never marks an attempt `successful` on its own, even when the gateway's `charge()` call reports `success: true`.** Every real driver in this app's catalog (`StripeDriver`'s Checkout Session, `MpesaDriver`'s STK push, and the rest by the same pattern) reports `charge()` success as "the gateway accepted the request and is now waiting on the customer" (a redirect URL to visit, a phone prompt to approve), not "money received" - so `charge()` only ever produces a `pending` or `failed` attempt. The *only* path to `successful` is `verifyAttempt()`, which re-queries the gateway's own status API (`PaymentGatewayInterface::verify()`) using the company's real stored credentials, and on confirmation calls `InvoiceService::recordPayment()` with `method: 'gateway'` - the same method Module 17's manual "Record a Payment" form uses for `cash`/`bank_transfer`/etc., just a different value, so a gateway-collected payment updates `invoices.status`/`amount_paid` through the exact same, already-tested code path as a manually recorded one. `invoice_payments.method`'s enum gained this `'gateway'` value via a dedicated migration (`RecordInvoicePaymentRequest`'s validation deliberately still excludes it - an admin's manual form can never claim a payment was gateway-collected; only `RentCollectionService` ever sets it).

**The inbound payment webhook (`POST /api/v1/webhooks/payments/{provider}`) is the first webhook endpoint in this codebase, and it deliberately never trusts the payload's claimed outcome.** It only uses the payload to identify *which* pending attempt to re-check (a best-effort per-provider reference extraction, not an exhaustive parser for all 12 drivers' exact payload shapes), then calls the same `verifyAttempt()` used everywhere else, which re-verifies against the real gateway API before ever recording money received. This sidesteps needing a bespoke, precisely-correct HMAC/signature verification implementation for each of the 12 payment drivers to be trustworthy - a spoofed request can, at worst, trigger a real (harmless) status re-check against a company's actual gateway account. The route is unauthenticated (no Sanctum token exists for an inbound gateway call) but throttled (`throttle:60,1`), satisfying §7's "rate limiting on... payment webhook endpoints" requirement, the first concrete application of that rule.

**`VerifyPendingRentPayments`, scheduled every 15 minutes, is a robustness net alongside the webhook, not a replacement for it** - this app has no persistent queue worker to react to a webhook instantly (§6), and not every real deployment will have a public, reachable webhook URL configured, so polling every still-pending attempt this often guarantees a successful charge gets recorded within a bounded time even if no webhook ever arrives. The same command also calls `RentCollectionService::expireStaleAttempts()`, which fails any attempt still `pending` after 24 hours - a pragmatic timeout, not a gateway-confirmed outcome, since `verify()`'s `success: false` can't distinguish "still processing" from "the customer cancelled." An expired attempt can never be resurrected; collecting again means a fresh `chargeInvoice()` call, mirroring Lease's "no editing past a lifecycle point" discipline (§10d) applied to a payment attempt instead of a lease/invoice record.

**Tenant gained the `Notifiable` trait in this module** - the only model in the app besides `User` to have it. `email`/`phone` already match Laravel's default notification routing conventions, and `CompanySmsChannel` (§5's Notifications module) already reads `$notifiable->company` directly (provided for free by `BelongsToCompany`), so no `routeNotificationFor*()` overrides were needed. Two new notifications, `InvoiceDueSoon` and `InvoiceOverdue` (`app/Modules/RentCollection/Notifications/`), both include `company-sms` alongside `database`/`company-mail` - a deliberate contrast with `TrialEndingSoon`'s email-only choice (§5), whose own docblock explicitly reserves SMS for "a stronger case (e.g. a failed payment)"; a rent-due/overdue reminder is exactly that case in this vertical. Neither includes a `url` in its `toArray()` - there's no Tenant Portal yet (Phase E) for a tenant to click through to.

**`SendRentReminders`, scheduled daily, fires `InvoiceDueSoon` exactly once per invoice, 3 days before `due_date`** (the same "exact day, not a rolling window" discipline `NotifyTrialsEndingSoon` established, §5) - a bare `invoice_id` dedupe check is sufficient, unlike `TrialEndingSoon`'s extra `trial_ends_at` sub-match, because `due_date` is immutable on a sent invoice (§10e's editable-only-while-draft rule) and so can never legitimately change out from under the dedupe. `InvoiceOverdue`, by contrast, *re-notifies every 7 days* while an invoice stays overdue - unlike a one-shot trial reminder, a debt still unpaid a week later deserves another nudge, not permanent silence, so its dedupe check is a rolling time window instead of a bare existence check.

**No new permission group.** Every action this module adds (`invoices.charge`, `invoices.payment-attempts.verify`) is gated by the existing `invoices.update` permission (§10e) - the same restraint applied to Lease's termination and Invoice's own send/cancel/recordPayment actions (§10d/§10e): these are state-changing actions on an existing Invoice, not a new entity with independent CRUD, so they don't warrant their own permission. `InvoicePaymentAttempt` itself has no `Gate::policy()` registration for the same reason `InvoiceItem`/`InvoicePayment` don't - it's a pure child/audit record, authorized through Invoice's policy in the controller, not independently.

**`RentCollectionSeeder` creates `InvoicePaymentAttempt` rows directly rather than through `chargeInvoice()`**, unlike `InvoiceSeeder`'s deliberate use of the service (§10e) - no seeded company has real payment gateway credentials (the Integrations module has no seeder/factory of its own), so routing through the service would just produce "no active payment provider" rejections for every attempt. A `'successful'` seeded outcome still goes through `InvoiceService::recordPayment()` for its matching `InvoicePayment`/status update, preserving the one part of this that *is* real business logic worth not reimplementing.

## 12. Accounting (`app/Modules/Accounting`) — built in Module 19, first module of Phase D

The first Phase D (Financial & Operations) module, and the foundational double-entry ledger every later Phase D module (Expenses, Vendors, ...) will eventually post against - not itself a real-estate domain entity any more than Rent Collection is (§11), but unlike Rent Collection it *does* add real domain entities of its own (a chart of accounts, journal entries) with independent CRUD screens, so it earns its own top-level `## 12` heading for a different reason: it's the financial foundation everything else in Phase D sits on top of, not an integration layer between two other modules.

**Three tables: `accounts`, `journal_entries`, `journal_entry_lines`** - standard double-entry bookkeeping shape. `Account.type` (`asset`/`liability`/`equity`/`income`/`expense`) drives `Account::balance()`'s sign convention (debit-normal for asset/expense, credit-normal for the rest) - the single place in the app that encodes this accounting rule. `journal_entry_lines.account_id` uses `restrictOnDelete()` (the same reasoning as `leases.tenant_id`/`unit_id`, §10d) - an account referenced by real ledger history can never be hard-deleted out from under it, though soft-deleting/deactivating it is still fine. `journal_entries` uses `nullableMorphs('source')` so an automatically-posted entry can link back to what generated it (an `Invoice`, an `InvoicePayment`) - manual entries simply leave it null.

**A posted journal entry is immutable - there is no `update()` on `JournalEntryService`, deliberately, and the service doesn't even extend `BaseService`** (unlike every other module's service so far) specifically so those inherited methods aren't dead surface someone could wrongly reach for. Correcting a mistake means `void()`, which posts a real reversing entry (every line's debit/credit swapped) and marks the original `voided` - ledger history is never edited or erased, standard accounting practice. Because of this, `Account::balance()` never needs to filter by `journal_entries.status` at all: a voided entry's reversal already nets it to zero on its own, so excluding voided entries from the sum would double-correct. `void` gets its own permission (`journal-entries.void`) rather than being folded under a generic `update`, unlike every other module's status-changing action (Lease's termination, Invoice's send/cancel/recordPayment, §10d/§10e/§11) - those modules fold such actions under `update` because a genuine `update` permission already exists for the same model; `JournalEntry` has no `update` action at all to fold `void` into.

**`JournalEntryService::post()` validates that every entry's lines balance (`sum(debit) === sum(credit)`) and total more than zero before persisting anything** - the one hard rule that makes it a real ledger and not just a list of transactions. `StoreJournalEntryRequest` additionally rejects any single line that's both a debit and a credit, or neither, at the HTTP layer before the service even sees it - a per-line shape problem the overall-balance check alone wouldn't catch.

**Revenue and cash receipts post themselves automatically, via Laravel's event system, not a direct call from Invoices into Accounting.** `InvoiceService::send()` now dispatches `Invoices\Events\InvoiceSent`, and `InvoiceService::recordPayment()` dispatches `Invoices\Events\InvoicePaymentRecorded` - both *after* their own `DB::transaction()` commits, never from inside one, so a failure in whatever listens can never roll back the invoice actually being sent or paid. Accounting's `PostInvoiceRevenueJournalEntry`/`PostInvoicePaymentJournalEntry` listeners (registered in `AccountingServiceProvider::boot()`) are the only things that know these events exist - Invoices has zero knowledge of Accounting, the exact same decoupling `Companies\Events\CompanyCreated` already established for `Users\Listeners\SeedDefaultRolesForCompany` (§3b). Sending an invoice posts `Dr Accounts Receivable (1200) / Cr Rental Income (4000)` for its total; recording a payment posts `Dr Cash (1000) or Bank (1100) / Cr Accounts Receivable (1200)` for the payment amount, choosing Cash vs. Bank by `method` (`bank_transfer`/`cheque`/`gateway` → Bank, everything else → Cash) - the exact "decimal-to-minor-unit conversion belongs at the integration boundary" note from Module 13's original ARCHITECTURE.md text, except this boundary is between this app's own domain (decimal) and its own ledger (also decimal, but now double-entried), not a third-party API.

**Both automatic-posting listeners fail soft, never hard**: if a company's default `1200`/`4000`/`1000`/`1100` account has been renamed, deactivated, or deleted, the listener logs a warning and returns - it never throws, and a bookkeeping-side problem can never surface as a broken "Send Invoice" button or a failed payment recording. This is a deliberate, stricter safety net than most of this app's other cross-cutting logic, because unlike (say) a failed SMS reminder, the *primary* action (sending an invoice, collecting rent) is unambiguously more important than its secondary bookkeeping side effect.

**`accounts.*` and `journal-entries.*` are two separate permission groups**, mirroring the `leases.*`/`invoices.*` split (§10d/§10e) rather than one combined `accounting.*` group - managing the chart of accounts (a structural, rarely-touched setup task) and posting day-to-day journal entries are different enough responsibilities that a company may reasonably want to grant one without the other (e.g. a bookkeeper who posts entries against a chart of accounts someone else maintains).

**`SeedDefaultChartOfAccountsForCompany` seeds a modest 12-account starter chart** (`config/accounting.php`'s `default_chart`) for every new company, the same `CompanyCreated`-triggered pattern as Module 3's default Admin/Staff roles. `ChartOfAccountsSeeder` is a one-time backfill (not part of `DatabaseSeeder::run()`'s normal sequence) for companies that existed before this module did - the same "re-run after a module ships" role `PermissionSeeder` plays for permission catalogs, since `CompanyCreated` already only fires once, at creation time, for companies created going forward.

**A real, documented limitation**: this module does not retroactively post journal entries for invoices sent/paid before it existed. `InvoiceSent`/`InvoicePaymentRecorded` only ever fire at the moment `InvoiceService::send()`/`recordPayment()` actually run - historical invoices seeded or processed in earlier sessions have no matching ledger entries, and there is no backfill command for this (unlike the chart-of-accounts backfill above) because correctly replaying historical state accurately would require more than this module's scope. New activity going forward is fully covered.

## 13. Expenses (`app/Modules/Expenses`) — built in Module 20

The second Phase D module, and the first to genuinely *consume* Accounting (§12) rather than just being consumed-from by it the way Invoices is - `Expense belongsTo Account` (which expense category: Maintenance, Utilities, ...) directly, not through an event. This is a deliberate, different coupling direction than Invoices→Accounting's event-based decoupling (§12): Accounting is a lower-level, foundational module every later Phase D module will sit on top of, so a direct dependency from Expenses down into Accounting's `JournalEntryService` is the same normal, expected direction as Rent Collection calling `InvoiceService`/`PaymentManager` directly (§11) - decoupling via events is for when a *lower*-level module (Invoices) needs to stay ignorant of a *higher*-level consumer (Accounting), not the reverse.

**An expense posts its ledger entry immediately at creation - there is no draft/send lifecycle the way Invoice has one.** An expense record isn't a document sent to a third party for approval; it's a fact being recorded (a bill received, a payment made), so `ExpenseService::create()` posts `Dr {category account} / Cr Accounts Payable (2000)` (if `payment_status: unpaid`) or `Dr {category account} / Cr Cash (1000) or Bank (1100)` (if `payment_status: paid`, chosen by `payment_method`) as part of the same request that creates the row.

**No `vendor_id` - just a free-text `vendor_name` column**, the deferred-FK pattern already established for `properties.landlord_id` (§10b): the Vendors module (Module 21) doesn't exist yet. A real `vendor_id` FK arrives when it does; nothing about this module's shape needs to change to add it later, the same way Properties didn't need restructuring when Landlords showed up a module later.

**`property_id` is nullable** - not every expense belongs to one property (a software subscription, a bank fee are company-wide), so unlike `invoices.lease_id` (always required, §10e), this is optional. When set, it's scoped to the acting company via the same `Rule::exists(...)->where('company_id', ...)` pattern as every other cross-tenant FK validation in this app.

**`payment_status` (has the bill been settled) and `status` (is this record still valid) are two separate lifecycles, not one.** `payment_status` moves `unpaid → paid` via `markAsPaid()`, which posts a second, *settlement* journal entry (`Dr Accounts Payable / Cr Cash or Bank`) reducing the payable back down - this is a real second transaction, not a correction to the first. `status` moves `active → voided` via `void()`, which reverses *every* journal entry this expense ever posted (both the initial one and, if it happened, the settlement one) - an expense that was marked paid and is later voided needs both halves of its ledger history reversed, not just the most recent action. Both lifecycles reuse Accounting's own primitives (`JournalEntryService::post()`/`void()`) rather than reimplementing balance/reversal logic.

**There is no `delete()` - `ExpenseService::delete()` always throws.** An expense always has at least one posted journal entry from the moment it's created (unlike Invoice, which is only ever deletable pre-posting, while still `draft`, §10e), so a hard delete would orphan real ledger history no matter when it happened. `void()` is the only way to retract one, the same discipline `JournalEntry` itself follows (§12) - Expense doesn't get its own `expenses.delete` permission as a result, since there's no action for it to gate.

**Only non-financial metadata is editable after creation** (`property_id`, `vendor_name`, `description`, `reference`, `notes`) - `UpdateExpenseRequest` doesn't accept `account_id`, `amount`, `expense_date`, or `payment_status` at all, the same "no editing past a lifecycle point" discipline as Invoice's fixed fields once sent (§10e) and Lease's fixed `tenant_id`/`unit_id` (§10d). Correcting an amount means voiding the expense and recording a new, correct one - editing it in place would desync the record from the ledger entry it already posted. `void` is gated by the existing `expenses.update` permission rather than its own (unlike `journal-entries.void`, §12) - Expense has a genuine `update` action to fold it into (editing metadata) that `JournalEntry` doesn't have at all.

**Both of `ExpenseService`'s posting paths fail soft, never hard** - the same discipline as Accounting's own `InvoiceSent`/`InvoicePaymentRecorded` listeners (§12): if a company's default `2000`/`1000`/`1100` account is missing, renamed, or inactive, the expense still saves, a warning is logged, and no journal entry is posted. Recording an expense (or marking one paid) can never fail because of a bookkeeping-side configuration problem.

**`ExpenseSeeder` goes through `ExpenseService`, the same reasoning as `InvoiceSeeder` (§10e)** - posting the journal entry is real business logic a seeder shouldn't reimplement or bypass. It also deliberately calls `markAsPaid()` on a portion of the unpaid expenses it creates, so seeded data exercises the settlement-posting path too, not just the initial one.

## 14. Vendors (`app/Modules/Vendors`) — built in Module 21

Closes the deferred-FK gap Module 20 deliberately left open: `expenses.vendor_id` (nullable, `nullOnDelete`) is added by this module's own migration, the exact same discipline as `properties.landlord_id` being added a module after Properties shipped (§10b) - Expense's shape didn't need to change to gain it, only a new column and a `belongsTo`.

**Vendor is a near-exact structural mirror of Landlord** (§10b): `type` (individual/company), address fields, `tax_id` unencrypted (needed for search/reporting, lower sensitivity), `bank_details` encrypted-but-not-masked (`encrypted:array`, the company's own reference data about who it pays, not a write-only third-party secret - identical reasoning to Landlord's bank details, assembled from five flat `bank_*` form fields in `VendorService` the same way `LandlordService` does), a single-file `photo` media collection, and the same no-SaaS-owner-bypass policy. The one real addition is `category` (plumbing/electrical/hvac/cleaning/landscaping/pest_control/general_contractor/utility_provider/security/other) - a genuinely useful filter dimension Landlord has no equivalent of, since "what kind of landlord" isn't a meaningful question the way "what kind of vendor" is.

**`vendor_id` and the pre-existing free-text `vendor_name` deliberately coexist on `expenses` - neither replaces the other.** Not every vendor is worth a formal record (a one-off purchase from an unfamiliar supplier), so the expense form offers both: a dropdown of known vendors, and a plain text field for anyone not on file. `Expense::vendorDisplayName()` is the one place display code needs to check - `$this->vendor?->name ?? $this->vendor_name` - so every view and the API resource ask "who was this paid to" the same way regardless of which was used. `vendor_id` is validated the same scoped-`Rule::exists` way as every other cross-tenant FK in this app (matching `properties.landlord_id`'s validation in `StorePropertyRequest`, §10b) and is accepted by both `StoreExpenseRequest` and `UpdateExpenseRequest` - unlike `account_id`/`amount`/`expense_date`/`payment_status`, which `UpdateExpenseRequest` locks after creation (§13), which vendor is credited is metadata, not a financial fact the ledger depends on, so it stays editable.

**`Vendor hasMany Expense`, shown inline on the vendor's own page** - the same "children shown on the parent's page" convention as Landlord's Properties list (§10b) and Tenant's lease history (§10c), giving a real, immediate answer to "what have we paid this vendor" without waiting for Phase E's Reports module.

**`VendorSeeder` runs after `CompanySeeder`, and `ExpenseSeeder` was updated to consume it** - roughly half of seeded expenses now link to a real seeded `Vendor` (matching category loosely isn't attempted; realism here is "some expenses have a formal vendor, some don't," not perfect category alignment), the other half keep using free-text `vendor_name` as before, so seeded data exercises both paths.

## 15. Maintenance (`app/Modules/Maintenance`) — built in Module 22

The capstone of Phase D's operational modules - a genuine payoff for everything Modules 13-21 built, not a new domain concept of its own. A `MaintenanceRequest` ties together Property (required), Unit/Tenant/Vendor (all nullable) and, via `recordExpense()`, Expenses itself (§13, which in turn posts to Accounting, §12) - closing the loop from "something's broken" to "here's the real, ledgered cost of fixing it."

**Four deferred FKs land on `maintenance_requests` in this module's own migration, not the other way around** - `unit_id`, `tenant_id`, `vendor_id` all `nullOnDelete`, `expense_id` also `nullOnDelete` - the same "the column arrives once its target module exists" discipline as `properties.landlord_id` (§10b) and `expenses.vendor_id` (§14), except here all four are deferred *within a single migration* rather than one at a time, since Maintenance is the first module built after every module it needs to reference already exists. `property_id` alone is `restrictOnDelete()` and required - a maintenance request always concerns exactly one property, the same non-negotiable anchor `invoices.lease_id` is to Lease (§10e).

**`category` reuses the exact same ten-value enum as `vendors.category`** (plumbing/electrical/hvac/cleaning/landscaping/pest_control/general_contractor/utility_provider/security/other) rather than a mapping table between two similar-but-different lists - a plumbing request and a plumbing vendor are the same concept from two sides, so matching one to the other by nothing more than an equality check is both simpler and more correct than any translation layer would be.

**`status` (open/in_progress/completed/cancelled) and the underlying financial record are two separate concerns, deliberately not auto-linked.** Marking a request `completed` does not create an expense - `MaintenanceRequestService::recordExpense()` is a distinct, explicit user action (its own button, its own form on the show page), only offered once a request has no `expense_id` yet. A maintenance record shouldn't silently spend money without a user confirming an actual amount; a request can be completed with no cost at all (a warranty repair, a tenant's own fix) just as validly as one that costs money.

**`completed_date` auto-sets itself the moment `status` transitions into `completed`, unless the caller already supplied one** - `MaintenanceRequestService::update()` checks `$model->status !== 'completed' && ($attributes['status'] ?? $model->status) === 'completed'` before calling through to `BaseService::update()`, the same system-derived-date pattern as `leases.terminated_at`/`invoices.paid_on` (§10d/§10e). Unlike those two, though, `completed_date` can still be edited directly afterward (`UpdateMaintenanceRequestRequest` accepts it) - a request completed today but only *logged* as completed a week later needs a way to record the true date, and there's no ledger integrity at stake in getting it wrong the way there would be for a financial timestamp.

**`recordExpense()` creates a real `Expense` through `ExpenseService::create()` - never a hand-rolled `Expense::create()`** - so a maintenance-triggered expense posts to the ledger exactly like any manually-recorded one (`Dr {category account} / Cr Accounts Payable or Cash/Bank`, §13), inheriting all of Expenses' own discipline (fail-soft posting, no delete, locked financial fields after creation) for free. The whole thing runs inside one `DB::transaction()`: create the `Expense`, then update the `MaintenanceRequest` with `expense_id` and `actual_cost` (copied from the expense's own `amount`, not re-entered) - both succeed or neither does. A second call against a request that already has one throws a `ValidationException` rather than silently creating a duplicate or overwriting the link.

**Unlike Expense, `MaintenanceRequest` has an entirely ordinary `delete()` - soft-delete, no voiding, no restrictions.** A maintenance request carries no ledger integrity concerns of its own (only its *linked* Expense does, and that record is untouched by deleting the request that pointed to it) - it's an operational record, not a financial one, so it follows the same plain CRUD discipline as Property or Tenant rather than Expense's "no delete, only void" rule (§13). `property_id` itself stays editable on update, too (unlike Expense's locked financial fields) - which property a request concerns is corrigible metadata here, not a fact the ledger depends on.

**Shown inline on both the Property's and the Vendor's own show pages** - the same "children on the parent's page" convention as Landlord's Properties list (§10b), Tenant's lease history (§10c), and Vendor's own Expenses list (§14) - each capped at the ten most recent requests, ordered by `reported_date`, so both pages answer "what's been reported here / assigned to them" without waiting for Phase E's Reports module.

**`MaintenanceRequestSeeder` runs last in `DatabaseSeeder::run()`**, after Property, Tenant, and Vendor seeders, since a request can reference all three. Roughly a third of seeded `completed` requests with a vendor attached also get a real `recordExpense()` call (through the service, the same "seeders shouldn't bypass real business logic" discipline as `ExpenseSeeder`, §13) - so seeded data exercises the full close-the-loop path, not just the request records on their own.

## 16. Inventory (`app/Modules/Inventory`) — built in Module 23

Two tables: `inventory_items` (the catalog) and `inventory_transactions` (an immutable, append-only stock ledger) - the same two-part shape as Accounting's chart of accounts / journal entries (§12), scaled down for physical stock instead of money. `InventoryTransaction` has no `SoftDeletes`, no `update()` path anywhere in the module, and its factory is explicitly documented as test-scaffolding-only, not a way to produce realistic history - correcting a mistake means logging a new offsetting `adjustment` transaction, the same "never edit history" instinct as `JournalEntry` (§12), just without the formal void-with-reversal ceremony, since the stakes (a stock count) are lower than money.

**`quantity_on_hand` is deliberately absent from `InventoryItem::$fillable`** - it is system-derived, changed only by `InventoryItemService::recordTransaction()`, never by a create/update request. `InventoryItemService::create()`/`update()` additionally strip the field from their attributes as defense in depth, mirroring `UpdateExpenseRequest`'s locked financial fields (§13), even though the model-level `$fillable` guard alone already prevents it. New items always start at zero; bringing real stock onto the books means recording a real `receipt` transaction right after creation, not backdooring an initial count into the create form. **A real bug caught during this module's own smoke testing**: `recordTransaction()` initially moved the balance with a plain `$item->update([...])`, which - because `quantity_on_hand` isn't fillable - silently discarded the change instead of erroring, so nothing actually moved. Fixed by using `forceFill()->save()` instead, the correct way to touch a deliberately-non-fillable system field from inside the module that owns it.

**`recordTransaction()` computes a signed delta from `type` and a caller-supplied positive magnitude, never a raw signed number from the form** - `receipt` is always `+magnitude`, `usage` is always `-magnitude`, and only `adjustment` asks the caller to choose a `direction` (increase/decrease). This mirrors the app's general preference for controlled selects over free-typed signed numbers (the same reasoning `RecordMaintenanceExpenseRequest`'s `payment_status` select embodies, §15). Every transaction stores `quantity` (the delta actually applied), plus `quantity_before`/`quantity_after` snapshots - a richer audit trail than a running total alone would give, the same instinct as `journal_entry_lines` recording debit/credit rather than a single signed number (§12). Stock can never go negative: if a `usage` or `decrease`-direction `adjustment` would take `quantity_on_hand` below zero, `recordTransaction()` throws a `ValidationException` before anything is written, surfacing as an ordinary form validation error - the same proven pattern as `JournalEntryService::void()`'s already-voided guard (§12).

**`maintenance_request_id` is a direct FK on `inventory_transactions`, not a deferred one** - unlike every deferred FK in earlier modules (`properties.landlord_id`, §10b; `expenses.vendor_id`, §14; Maintenance's four FKs, §15), Maintenance (Module 22) already exists by the time this module is built, so there's nothing to defer. It's populated only on the *item's* side, when recording a `usage` transaction against a specific request (an optional dropdown on the item's own "Record Transaction" form) - deliberately not a new action added to Maintenance's own page, since that would need cross-page item-selection UI for no real benefit. `MaintenanceRequest::inventoryTransactions()` (added to the Module 22 model in this module's own edit, the same "add the inverse relation to the earlier module" pattern as Property/Vendor's `maintenanceRequests()`) is purely a read-only byproduct on that side - the request's own show page gains a "Parts Used" section populated by these rows, with no button or action of its own that creates them.

**`InventoryItem` gets an entirely ordinary soft `delete()` - the same reasoning as `MaintenanceRequest` (§15), not Expense's "no delete, only void" (§13).** The item catalog entry is operational metadata; the real ledger is its `transactions`, and those are `restrictOnDelete`-protected at the database level and completely untouched by soft-deleting the parent item - deleting an item hides it from the catalog, it doesn't erase or orphan its stock history.

**Two independent "children on the parent's page" wirings**, both following the established convention (§10b/§14/§15): Property's show page gains an Inventory card (items where `property_id` matches, capped at ten, with a "New Item" button that pre-fills the property the same way Maintenance's did) and Vendor's show page gains an "Inventory Items Supplied" card (items where `vendor_id` matches) - `property_id` and `vendor_id` are both nullable on `InventoryItem`, since plenty of stock (bulk cleaning supplies, a shared tool pool) belongs to neither one property nor one supplier specifically.

**`InventoryItemSeeder` runs last in `DatabaseSeeder::run()`, after Property/Vendor/MaintenanceRequest**, and goes entirely through `InventoryItemService::recordTransaction()` for every seeded stock movement (never a raw `InventoryTransaction::create()`) - the same "seeders shouldn't bypass real business logic" discipline as `ExpenseSeeder`/`MaintenanceRequestSeeder` (§13/§15), required here specifically because `quantity_on_hand` must stay mathematically consistent with its own transaction history, which only the service's own atomic before/after bookkeeping guarantees.

## 17. Documents (`app/Modules/Documents`) — built in Module 24

The most cross-cutting module in Phase D by nature, not by accident - a `Document` is a real, downloadable file (Spatie Media Library, the same primitive already backing Company's logo and every photo collection) plus queryable metadata (`title`, `category`, `expiry_date`), optionally attached to **any one of five earlier entities** - Property, Landlord, Tenant, Lease, or Vendor - via a nullable polymorphic pair, or left standing alone as a company-wide record (a business license, a master insurance policy has no single property to belong to).

**`documentable_type`/`documentable_id` store the real FQCN, the same convention `journal_entries.source_type`/`source_id` already established (ARCHITECTURE.md §12)** - no `Relation::morphMap()` override, and deliberately no database FK constraint on either column, for the identical reason a polymorphic column never gets one. Requests and views never work with the raw class name directly, though: `Document::documentableTypeMap()` is the one source of truth mapping five short, form-facing keys (`property`/`landlord`/`tenant`/`lease`/`vendor`) to their real classes, and `documentableRouteMap()` does the same for building a link to wherever a document is actually attached. `documentableTypeKey()` reverses a stored FQCN back to its short key for display. Every place that needs to reason about "what kind of thing can a document attach to" reads this one map - adding a sixth attachable type later means extending it in exactly one place, plus a `documents()` `morphMany` relation on the new model.

**A document's attachment is fixed at upload time - `UpdateDocumentRequest` doesn't accept `documentable_type`/`documentable_id` at all**, the same "locked after creation" discipline as `leases.tenant_id`/`unit_id` (§10d) - re-pointing an uploaded contract at a different property isn't a real workflow this app needs to support. Deleting and re-uploading is the correct way to fix a genuine mis-attachment.

**The create form only exposes a documentable choice as hidden, pre-resolved fields, never a live dropdown spanning all five entity types at once** - navigating to `/documents/create` directly creates a standalone, company-wide document; arriving via an "Add Document" button from a specific Property/Landlord/Tenant/Lease/Vendor's own show page pre-fills and locks `documentable_type`/`documentable_id` as hidden inputs, with the target's real name shown read-only (`DocumentController::labelFor()` special-cases `Lease`, which has no `name` column of its own, to `"Lease #{id} — {tenant name}"`). A single combined picker across five different tables' worth of records would be unwieldy UI for a rare workflow; this app's answer is the same one Maintenance's create form already gave for its property pre-fill (§15) - a query-string-driven pre-selection - just extended to a type *and* an id instead of one FK alone.

**File storage reuses `StorageResolver::diskFor($company)` and the exact `addMedia()`-inside-`DB::transaction()` shape `CompanyService::updateBranding()` already established** (this module's only real precedent for a genuine end-to-end file upload flow in this app - Vendor's `photo` collection exists on the model but was never wired to an upload form, a pre-existing gap this module didn't need to fix). `DocumentService::create()`/`update()` both pull `'file'` out of the attributes array before handing the rest to the repository, so a `Document` can exist with no file at all (`fileUrl()` returns null gracefully everywhere it's read) - useful for a metadata-only placeholder, though the web/API `Store` request does require one; only `Update` makes it optional, replacing the existing file only if a new one is sent, mirroring the branding flow's own nullable-logo shape exactly.

**A real, documented limitation, the same honest-about-gaps discipline as Accounting's retroactive-posting note (§12)**: every file URL in this app, Documents included, is served via `getFirstMediaUrl()` - a plain, unsigned URL. The original Phase 1 architecture plan called for signed/temporary URLs once a company's storage disk is cloud-based; no module has actually implemented that yet, Documents included, even though it's the module where getting this right matters most (ID scans, signed contracts). This is a known, pre-existing gap this module inherits rather than introduces, and a natural candidate for hardening whenever the Public REST API/security pass (Phase E) revisits file serving app-wide.

**`DocumentSeeder` runs last in `DatabaseSeeder::run()`, after Property/Landlord/Tenant/Lease/Vendor**, and goes entirely through `DocumentService::create()` with a real `UploadedFile::fake()`-generated PDF for every seeded row (never a raw `Document::create()`) - the same "seeders shouldn't bypass real business logic" discipline as every other Phase D seeder, required here specifically because the file itself has to exist as real, downloadable media, not just a database row.

## 18. Visitor Management (`app/Modules/VisitorManagement`) — built in Module 25, completing Phase D

The last Phase D module - a `Visitor` is a single check-in/check-out record: who arrived, at which Property (required, `restrictOnDelete`, the same "historical record about a property, not a structural part of it" reasoning as `maintenance_requests.property_id` and `documents`, §15/§17), optionally which Unit, optionally who they're visiting (a Tenant via `tenant_id`, or free-text `host_name` for staff/landlord/building management - the same coexisting-FK-and-free-text shape as `expenses.vendor_id`/`vendor_name`, §14), and optionally which Vendor they represent (a contractor's rep arriving to do work).

**No separate `status` column - `check_out_at`'s nullability alone is the entire state machine.** `isCheckedIn(): bool` is just `check_out_at === null`. This is deliberately simpler than Lease's `status` enum *plus* `terminated_at` (§10d): Lease genuinely has three states (active/expired/terminated) that a single timestamp can't distinguish, but a visit only ever has two - on-site or departed - so one nullable timestamp is both necessary and sufficient, and a redundant enum alongside it would just be one more field that could drift out of sync with the truth.

**`VisitorService::checkOut()` is the only place `check_out_at` is ever set - the update form doesn't accept it at all**, the same "closing action is a distinct, deliberate button, not a field on the general edit form" discipline as `MaintenanceRequestService::recordExpense()` (§15). It's gated by the existing `visitors.update` permission rather than its own, the same restraint applied there too. Checking out a visitor who already checked out throws a `ValidationException` (`'check_out_at' => 'This visitor has already checked out.'`) - the same "guard against re-doing a closing action" pattern as `JournalEntryService::void()`'s already-voided guard (§12) and `MaintenanceRequestService::recordExpense()`'s already-recorded guard (§15).

**Wired a `visitors()` relation onto two earlier models - Property and Tenant - not all four it can reference.** Unlike Documents, which wired its inline card onto all five entities it can attach to (§17), Visitor Management deliberately stops at the two anchors a front-desk user actually thinks in terms of: "who's been to this property" and "who's come to see this tenant." Unit and Vendor stay real, validated FKs on the record itself, but don't get their own inline card - a visitor's connection to a specific unit or vendor is incidental detail on the visit, not something either of those pages' own users would naturally go looking for the way a property manager or the tenant's own record naturally would.

**`VisitorSeeder` runs last in `DatabaseSeeder::run()`, after Property/Tenant/Vendor**, mixing checked-in and checked-out visits (roughly 70% checked out) so seeded data exercises both states of the one real lifecycle this module has.

This completes **Phase D (Financial & Operations)** - Modules 19 through 25. Phase E (Portals, Reporting, API, AI) is next.

## 19. Tenant Portal (`app/Modules/TenantPortal`) — built in Module 26, first Phase E module

The first module to introduce a genuinely new identity in this app - not a company staff member (the `web` guard, Spatie-permission-gated) and not a SaaS-owner, but a `Tenant` logging into their own self-service area: their lease, their invoices (with the ability to pay online), their maintenance requests (with the ability to submit new ones), and their documents. Read-only where read-only is right, but two real write actions (paying, reporting an issue) where a portal that could only ever look at things wouldn't be worth building.

**`Tenant` now extends `Illuminate\Foundation\Auth\User` instead of the plain Eloquent `Model` - the exact same base class `App\Models\User` itself extends.** This is a drop-in swap (that base class already extends `Model`, so every existing Tenant behavior - CRUD, media, activity log, the Documents/VisitorManagement relations from Modules 24-25 - is untouched for the vast majority of tenants who never get portal access) that makes `Tenant` a real `Authenticatable` for its own `tenant` guard. `password`/`remember_token` were added via this module's own migration on the `tenants` table (the deferred-column pattern already established repeatedly, e.g. `expenses.vendor_id`, §14) - both deliberately absent from `Tenant::$fillable`, the same "system-derived, only touched by its owning service" discipline as `inventory_items.quantity_on_hand` (§16): only `TenantPortalService::enableAccess()`/`disableAccess()` ever set them, via `forceFill()`.

**A second, wholly independent guard - `config('auth.guards.tenant')`, backed by a `tenants` provider - sits alongside `web`, not inside it.** No Spatie Permission involvement at all: tenants were never part of the Users/Roles/Permissions system (§3), and forcing them into it just to gate five portal screens would be a heavier abstraction than the problem needs. Every portal controller instead does a direct, explicit ownership check (`$lease->tenant_id === $tenant->id`, `$invoice->lease->tenant_id === $tenant->id`) - simpler than a Policy class for a guard where there's exactly one relevant question ("is this yours?") rather than a matrix of permissions.

**A real bug, caught and fixed by the automated test suite itself, that would otherwise have been a serious tenant-isolation hole**: `App\Core\Http\Middleware\IdentifyCompany` resolves the acting company from `$request->user()` (no explicit guard) - correct for `web` (session, no timing dependency) and for Sanctum-authenticated API requests (the `api-tenant` group's `auth:sanctum` middleware calls `Auth::shouldUse('sanctum')` before this middleware runs). It is NOT correct for the new `tenant` guard on its own: this middleware is appended to the very end of the `web` group (bootstrap/app.php), which means it runs on every portal request too, but *before* the portal's own route-level `auth:tenant` middleware gets a chance to call `shouldUse('tenant')`. The first fix attempt (`$request->user('web') ?? $request->user('tenant')`) traded one bug for a worse one - it broke `company_id` resolution for every Sanctum-authenticated API request across the entire app (47 test failures on the first full-suite run), since it no longer asked the default/Sanctum-switched guard at all. The correct fix is additive, not a replacement: `$request->user() ?? $request->user('tenant')` - the original no-guard call still covers `web` and `sanctum` exactly as before, and the explicit `tenant` fallback only kicks in for the one guard where the ordering assumption doesn't hold.

**Login is deliberately manual, not `Auth::attempt()`'s generic credential-array mechanism.** `tenants.email` has no database-level uniqueness constraint (plenty of tenants without portal access might coincidentally share one) - `TenantPortalService::enableAccess()` is the only place uniqueness is enforced, and only among tenants who *have* portal access (`whereNotNull('password')`), checked globally across companies, not per-company (the same reasoning `users.email` is already globally unique for company staff - a single shared login page has no company context yet to scope by). `PortalAuthController::login()` therefore looks up `Tenant::withoutGlobalScope('company')->whereNotNull('password')->where('email', ...)->first()` and calls `Hash::check()` itself, rather than risking `Auth::attempt()`'s generic mechanism calling `Hash::check()` against a `null` password for a same-email tenant who never got portal access.

**Guest routing had to become guard-aware.** Laravel's default `Authenticate` middleware only knows one `login` route unless told otherwise; `bootstrap/app.php` now calls `$middleware->redirectGuestsTo(fn ($request) => $request->is('portal*') ? route('portal.login') : route('login'))` so an unauthenticated hit on a portal route lands on the portal's own login page, not the staff one.

**`RentCollectionService::chargeInvoice()` needed zero changes to support tenant-initiated payments** - its `?User $initiator = null` parameter (Module 18) was already nullable, since not every charge was ever guaranteed to be staff-initiated. `PortalInvoiceController::pay()` simply calls it with `null`; `invoice_payment_attempts.initiated_by_id` stays null for a self-service payment, exactly as it would for any other staff-omitted charge. This is the same "the newer module reuses the older one directly, no event indirection needed" relationship Expenses has with Accounting (§13) - Module 26 is unambiguously the higher-level consumer here.

**Maintenance requests are submitted against a `lease_id`, never a raw `property_id`/`unit_id` pair** - `PortalStoreMaintenanceRequestRequest` validates the lease belongs to the authenticated tenant (`Rule::exists('leases','id')->where('tenant_id', $tenant->id)`), and `PortalMaintenanceRequestController::store()` derives `property_id`/`unit_id` from that lease server-side. This makes submitting a request against a property or unit the tenant has no relationship to structurally impossible, rather than something a scoped validation rule has to catch after the fact - a stricter version of the same instinct behind every other cross-tenant `Rule::exists()->where('company_id', ...)` in this app.

**The portal's Documents list merges two sources**: documents attached directly to the tenant (`documentable_type = Tenant`) and documents attached to any of their own leases (`documentable_type = Lease`, `documentable_id` in their lease ids) - a tenant's lease agreement is realistically attached to the *lease*, not the tenant record, and a portal that only checked one of the two would quietly hide it.

**A deliberate, documented scope cut: web only, no API surface for this module** - the same restraint Module 3 already applied to Role management (§3b). A browser-based self-service portal doesn't need its own versioned JSON API in this phase; Module 30 (Public REST API hardening) is where the *staff-facing* API gets its next real pass, and a tenant-facing API (a mobile app, say) is a plausible future module of its own rather than something to bolt onto this one.

**`TenantPortalSeeder` runs last in `DatabaseSeeder::run()`**, and deliberately does NOT use `TenantPortalService::enableAccess()`'s own randomly-generated password - local dev needs a login it can actually type, so it sets a fixed, known password (`'password'`, the same convention `UserFactory` already uses for staff) directly via `forceFill()`, one portal-enabled tenant per company with an active lease.

## 20. Landlord Portal (`app/Modules/LandlordPortal`) — built in Module 27

A third independent identity alongside `web` and Module 26's `tenant` guard - a `Landlord` logging into their own read-only reporting area: their properties, the expenses recorded against them, maintenance activity, and documents. Built entirely on the same infrastructure Module 26 already established (`Illuminate\Foundation\Auth\User` base-class swap, a deferred `password`/`remember_token` migration, a manual-lookup login controller, admin-side enable/disable on the landlord's own page) - this module's real work was extending that shared infrastructure to a third guard correctly, and drawing the scope line in a genuinely different place than Module 26's.

**`Landlord` now extends `Illuminate\Foundation\Auth\User`, the identical drop-in base-class swap `Tenant` got in Module 26** - `password`/`remember_token` added via this module's own deferred migration on `landlords`, both absent from `$fillable`, `email` uniqueness enforced only among portal-enabled landlords by `LandlordPortalService::enableAccess()`, not a database constraint. `LandlordPortalAuthController::login()` does the identical manual `whereNotNull('password')`-scoped lookup + `Hash::check()` that `PortalAuthController` does for tenants, for the identical reason.

**`config('auth.guards')` now has three entries, not two** - `web`, `tenant`, and `landlord`, all session-driven, all backed by their own Eloquent provider. `App\Core\Http\Middleware\IdentifyCompany` was extended a second time: `$request->user() ?? $request->user('tenant') ?? $request->user('landlord')` - the same reasoning as Module 26's fix (ARCHITECTURE.md §19), just with one more explicit fallback. Because this was purely additive to a chain that already worked, it did not reproduce Module 26's Sanctum-breaking mistake - the lesson from that bug (never replace the original no-guard call, only extend the fallback chain) held on the first attempt this time, and the full test suite confirmed it with zero regressions.

**A wholly different scope line than Module 26, deliberately: read-only, no write actions at all.** Tenant Portal has two genuine self-service transactions (paying an invoice, reporting an issue) because a tenant is the one party positioned to take either action. A landlord in this app's model is a reporting subject, not an actor in daily operations - they don't pay themselves, and property managers, not landlords, are the ones who verify and file maintenance requests. Building "submit a request" or "record something" into this portal to mirror Module 26's shape for its own sake would be scope creep, not parity; the portal's entire job here is transparency into data staff/tenants already generate elsewhere.

**Financial visibility is computed directly in `LandlordPortalDashboardController`, not through a new relation on `Landlord`, because the underlying join is four tables deep.** `Landlord::expenses()`/`maintenanceRequests()` are genuine `hasManyThrough(..., Property::class)` relations (Laravel's `HasManyThrough` supports exactly one intermediate table, and both of these are a real two-hop join), but "rent collected across a landlord's properties" is `Landlord → Property → Building → Unit → Lease → Invoice`, a four-hop chain no single Eloquent relation type expresses cleanly - so the dashboard controller queries it directly (`Invoice::whereHas('lease.unit.building.property', fn ($q) => $q->where('landlord_id', ...))->sum('amount_paid')`) rather than forcing an artificial relation onto the model for a query used in exactly one place.

**A real bug, caught and fixed before the test suite even ran, from applying Module 26's own hard-won lesson early**: both `expenses` and the `properties` table `Landlord::expenses()`/`maintenanceRequests()` join through have their own `status` column - any unqualified `->where('status', ...)` against either `HasManyThrough` relation would have hit the exact SQLite "ambiguous column name" failure the automated test suite caught for `tenants.invoices()` in Module 26 (ARCHITECTURE.md §19). Every status filter here (`expenses.status` in the dashboard's total-expenses query) was written qualified from the start.

**The portal's Documents list merges two sources, the same shape as Module 26's**: documents attached directly to the landlord, plus documents attached to any of their own properties (a title deed, most commonly) - not their tenants' documents, and not documents on properties they don't own.

**The same deliberate, documented scope cut as Module 26: web only, no API surface.**

**`LandlordPortalSeeder` runs last in `DatabaseSeeder::run()`**, mirroring `TenantPortalSeeder` exactly - a fixed, known password (`'password'`) rather than `enableAccess()`'s random one, one portal-enabled landlord per company with at least one property.

## 21. Reports (`app/Modules/Reports`) — built in Module 28

The first module with genuinely no new tables at all - every report is a pure, read-only aggregation over data every earlier module already owns, and the module's real job is presentation: an on-screen Bootstrap view plus a PDF (DomPDF), Excel (`.xlsx`), and CSV download of the exact same data, for each of four reports - Rent Roll, Occupancy, Income Statement, and AR Aging. `barryvdh/laravel-dompdf` and `maatwebsite/excel` have been installed since Module 1 specifically for this module and had never been used until now.

**No repository, no BaseService, no Policy - each report is a single-method service class (`RentRollReportService::generate()`, etc.) called directly by the controller.** There's nothing to create/update/delete here, so the CRUD-shaped base classes every domain module extends would be pure ceremony. Authorization is a single `reports.view` permission checked via `$this->authorize('reports.view')` with no Policy class at all - Spatie Permission's `Gate::before` hook already makes any registered permission name checkable this way (the same pattern Module 4's Settings controller established for its own non-CRUD screens), so a Policy tied to a nonexistent "Report" Eloquent model would be inventing a resource that doesn't exist.

**Company scoping is entirely free - no report service takes a `companyId` parameter.** Every query (`Unit::query()`, `Property::query()`, `Account::query()`, `Invoice::query()`) already carries `BelongsToCompany`'s global scope, the same as every other query in this app; a report is just an aggregation on top of already-tenant-scoped data.

**The Income Statement reuses `Account::balance()`'s own sign convention for a date-ranged figure, rather than reimplementing it.** `balance()` (§12) already prefers `$this->debit_total`/`credit_total` when present on the model instead of running its own all-time `lines()->sum()` query - so `IncomeStatementReportService` aliases its date-scoped `withSum()` calls to those exact two names, and an ordinary `$account->balance()` call becomes a correctly-signed, date-ranged figure for free, with zero duplicated debit/credit-normal logic. The date filter itself never touches `journal_entries.status`, the same reasoning as everywhere else `balance()` is used: a voided entry's reversal already nets to zero on its own.

**A real bug caught by the automated test suite on first run, not by design**: `PdfFacade::loadView(...)->download(...)` returns `Illuminate\Http\Response`, not `Symfony\Component\HttpFoundation\BinaryFileResponse`/`StreamedResponse` as originally (incorrectly) type-hinted on every export action - a `TypeError` at the PHP level, not a Laravel-level failure, since the actual object returned violated the declared return type. Fixed by widening every export method's return type to `Symfony\Component\HttpFoundation\Response`, the common parent both DomPDF's and Laravel Excel's actual return values genuinely share.

**A second real bug, also caught by the test suite**: `ArAgingReportService`'s bucket totals used `Collection::sum()` directly, which returns int `0` (not float `0.0`) for an empty bucket - so a report with, say, no `over_90` invoices at all would have that one total silently typed differently (`int`) than every other, non-empty bucket's total (`float`), an inconsistency a strict-typed test assertion caught immediately even though no view or export would ever have visibly broken from it. Fixed with an explicit `(float)` cast on every bucket total and the grand total, so the return shape's types are guaranteed regardless of the underlying data.

**One generic `ReportExport` class, not four near-identical Maatwebsite Excel classes.** Every report's Excel/CSV shape is the same underlying primitive (rows of cell values, a heading row, a sheet title) - `ReportExport implements FromArray, WithHeadings, WithTitle` takes all three as constructor arguments, and each report's own controller action is responsible for flattening its (sometimes grouped, sometimes flat) data into that shape before handing it off. The Income Statement and AR Aging exports, which have real sectioned/grouped structure on-screen, are flattened into a single ordered row list (section header rows, data rows, subtotal rows) for the spreadsheet - a standard, readable convention for exporting a grouped report to a flat file format.

**PDF views are deliberately separate, minimal-CSS templates (`reports::pdf.*`), not the same Bootstrap views rendered twice.** DomPDF's rendering engine doesn't support Bootstrap 5's modern CSS (flexbox, custom properties) reliably, so each report gets its own plain-table PDF template with inline `<style>` - a real, necessary duplication between the on-screen and PDF views, not an oversight.

**A deliberate, documented scope cut: web only, no API surface** - the same restraint as Modules 3, 26, and 27. A report's natural interface is a browser view or a file download, not a JSON payload; there is no headless-client use case for this module in the current phase.

## 22. Subscriptions & Billing (`app/Modules/Subscriptions`) — built in Module 29

The SaaS owner's own side of the business: a catalog of subscription plans, each company's subscription to one of them, the SaaS owner's own invoices billing companies for that subscription, and - the module's real payoff - actually enforcing `companies.status` (present since Module 2, never once checked anywhere before now). Three new tables: `subscription_plans`, `subscriptions`, `subscription_invoices`. None of them carry `company_id`-scoped `BelongsToCompany` in the usual sense on `subscription_plans` (it's a platform-wide catalog, not tenant data), and `subscriptions`/`subscription_invoices` deliberately don't use the `BelongsToCompany` trait either, even though they do have a `company_id` column - they're data *about* a company, managed by the SaaS owner, not data a company's own users create or operate on, so `SubscriptionPolicy`/`SubscriptionInvoicePolicy` (not a tenant global scope) are what actually gate access.

**`subscriptions` is an immutable history table, the same convention as `journal_entries` (§12) and `inventory_transactions` (§16).** There is no "update a subscription's plan or dates" operation. Changing plans (`SubscriptionService::changePlan()`) and renewing (`renew()`) always **insert a new row**; the superseded row is left alone, untouched forever - it wasn't canceled, it was superseded. `Company::currentSubscription()` resolves "current" by finding whichever row was created most recently (`latest('current_period_start')->latest('id')`, `id` as the deterministic tie-breaker - see the bug note below). The one deliberate exception is `extendTrial()`, which mutates the current trialing row's `current_period_end` in place: extending a still-open trial period is not the same kind of operation as closing one out and starting the next.

**Two distinct severities when a subscription lapses, on purpose.** A trial that ends without converting to a paid plan suspends the company outright (`ExpireSubscriptions`, scheduled daily) - a trial that never converted has no standing to keep using the app. A *paid* subscription that lapses without renewal is only flagged `past_due`, never auto-suspended - a real billing failure deserves a grace period and a human decision, not an instant lockout the moment an invoice goes unpaid; suspending a `past_due` company remains a deliberate, manual SaaS-owner action (there is no automatic path from `past_due` to `suspended`).

**`EnsureCompanyIsActive` is the module's actual payoff.** Appended to both the `web` and `api-tenant` middleware groups, right after `IdentifyCompany`, it reads `CompanyContext::id()` (not `$request->user()` directly) - the same reasoning `IdentifyCompany` itself established (§19): one check covers all three guards (`web`, `tenant`, `landlord`) for free. A company with status `suspended` or `cancelled` gets a 403 on every request; a company on `trial` is deliberately **not** blocked here - a trialing company must keep full access for the trial to mean anything. SaaS-owner staff (no company context at all) and guests always pass through untouched. Logout routes (`logout`, `portal.logout`, `landlord-portal.logout`) are explicitly exempted - a suspended company's own user must always be able to sign out, or they'd be permanently trapped on a 403 page.

**Authorization is `isSaasOwner()`-direct, the same shape as `CompanyPolicy` (§3a), not a new permission family.** `SubscriptionPlanPolicy` is SaaS-owner-only on every ability (the plan catalog is a platform concern no company ever browses or edits). `SubscriptionPolicy`/`SubscriptionInvoicePolicy` mirror `CompanyPolicy` exactly: `viewAny`/`create`/`update` are SaaS-owner only, `view` additionally allows a company's own users to see their own subscription/invoices - no dedicated `config/permissions.php` entries exist for this module, the same reasoning `CompanyPolicy` itself never needed any.

**Two distinct entry points into the same underlying data**, matching who's looking: `CompanySubscriptionController`/`SubscriptionInvoiceController` are the SaaS-owner-side actions (change plan, reactivate, extend trial, renew, cancel, generate/mark-paid/void an invoice), wired directly into Company's own show page (`companies::show`) - the same "actions live where the record is already displayed" convention as the Tenant/Landlord Portal Access cards (§19/§20). `BillingController` is the company-facing counterpart: a single read-only `billing::index` page showing a company's own current plan and invoice history, with no state-changing actions at all.

**Three real bugs, all caught and fixed during this module's own build, before any test was written:**

- `EnsureCompanyIsActive`'s first draft had no exemption for logout routes at all - a suspended company's own user hitting their own logout button would themselves be blocked by the 403, permanently trapping them with no way to sign out. Fixed with the `EXEMPT_ROUTES` check described above.
- `CompanySubscriptionController::reactivate()` was first authorized via `$this->authorize('update', $company)` - `CompanyPolicy::update()` also permits the company's *own* admin, meaning a suspended company could theoretically un-suspend itself, defeating the entire point of the middleware above. Fixed with an explicit `abort_unless($request->user()->isSaasOwner(), 403)` instead of the Policy check.
- `ExpireSubscriptions`' first draft would flag *any* `active`-status subscription row with a lapsed `current_period_end` as `past_due` - including old, superseded rows left behind by a renewal or plan change (per the immutable-history design above, an old row's own `status`/dates are never touched again). Fixed by first resolving each company's actual current subscription id via a `MAX(id) GROUP BY company_id` subquery, then scoping both the trial-expiry and past-due queries to only that set of ids.

**A fourth bug, caught live while seeding sample data against the real database, after the automated test suite already passed:** `Company::currentSubscription()`'s original `latest('current_period_start')` alone is not a reliable "most recent" ordering, because `current_period_start` is a `date` column with no time-of-day component - two rows created on the same calendar day (e.g. a trial upgraded to a paid plan the same day it started) tie on that column, and the tie-break is undefined. Confirmed live: a company with two subscription rows created the same day resolved to its *older*, superseded trialing row instead of the newer active one. Fixed by adding `->latest('id')` as a deterministic secondary sort - rows are always inserted in creation order and never backdated, so `id` is a safe proxy for "actually most recent" whenever the date column alone ties.

**A fifth, unrelated bug caught the same way:** `SubscriptionInvoice` imported the `SoftDeletes` trait but never actually applied it in the class body (`use Illuminate\Database\Eloquent\SoftDeletes;` present, `use SoftDeletes;` inside the class missing) - invisible until something called `withTrashed()`/`onlyTrashed()`/soft-delete-aware query methods on the model, which `SubscriptionInvoiceService::nextInvoiceNumber()`'s `SubscriptionInvoice::withTrashed()->count()` does on every single invoice generated. Fixed by adding the missing `use SoftDeletes;` to the class.

**A deliberate, documented scope cut: no enforcement of `subscription_plans.max_properties/max_units/max_users` anywhere.** Enforcing a plan's limits at Property/Unit/User creation time would require those lower-numbered modules (§10a, §3b) to reach forward into this higher-numbered one, violating the "earlier modules stay ignorant of later ones" principle event-based decoupling exists specifically to preserve (e.g. Invoices → Accounting, §12). The limits are informational-only in this module's scope; enforcing them is a future module's job, most naturally implemented as an event listener on creation (the same shape as `SeedDefaultTrialSubscription` below) rather than a change to Properties/Units/Users themselves.

**`SeedDefaultTrialSubscription` listens for `Companies\Events\CompanyCreated`**, the same trigger as `SeedDefaultRolesForCompany` (§3b) and `SeedDefaultChartOfAccountsForCompany` (§12) - every new company is automatically put on a trial of whichever *active* plan is currently cheapest. It fails soft (logs a warning, never throws) if no active plan exists yet, the same "an automatic listener must never block the action it's reacting to" discipline as Accounting's invoice-posting listeners (§12) - a company must always be creatable even before the SaaS owner has configured any plans. `SubscriptionPlanSeeder` (three tiers: Starter/Growth/Enterprise) therefore has to run *before* `CompanySeeder` in `DatabaseSeeder::run()`, or every seeded company would silently get no subscription at all. `SubscriptionBackfillSeeder` is a standalone, non-`DatabaseSeeder`-wired backfill (the same role `ChartOfAccountsSeeder` plays for §12) for companies that existed before this module did - it uses each company's own pre-existing `status`/`trial_ends_at` to decide whether to seed a trialing or active subscription, rather than putting an already-active company back on a fresh trial it never actually had.

**A deliberate, documented scope cut: web only, no API surface** - the same restraint as Modules 3, 26, 27, and 28.
