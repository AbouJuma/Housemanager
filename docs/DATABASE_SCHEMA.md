# Database Schema

Grows incrementally as each module lands — one section per module, in build order. See [ARCHITECTURE.md §9](ARCHITECTURE.md#9-module-build-order-roadmap) for the roadmap.

## Conventions (apply to every tenant-owned table from Module 2 onward)

- `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY` — internal key, used for joins/indexes.
- `uuid CHAR(36) UNIQUE` — public/external identifier (route binding, API). Generated by `App\Core\Concerns\HasUuid`.
- `company_id BIGINT UNSIGNED` — tenant owner, indexed as `(company_id, id)`. Enforced/stamped by `App\Core\Concerns\BelongsToCompany`.
- `deleted_at TIMESTAMP NULL` — soft deletes on all business tables.
- `created_at` / `updated_at` — standard Eloquent timestamps.

## Module 3 — Users, Roles & Permissions

`users` (Laravel's base table, altered by this module's migration): gained `uuid` (unique, nullable — see the conventions note below) and `company_id` (nullable, FK to `companies`, `nullOnDelete`). `company_id === null` marks SaaS-owner staff, per the tenancy model.

Note on `uuid` nullability here specifically: unlike every table created fresh from Module 2 onward, `users` already existed with rows before this migration, so the new column can't be `NOT NULL` without a doctrine/dbal-dependent `->change()`. It's `nullable()` at the DB level; the migration backfills existing rows, and `HasUuid`'s `creating` hook guarantees every row created through Eloquent from here on has one — same practical guarantee as everywhere else, just without the DB-level constraint enforcing it retroactively.

Spatie Permission's package tables (`php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider"`, `config/permission.php` with `'teams' => true` and `'team_foreign_key' => 'company_id'`):

| Table | Team-scoped? | Notes |
|---|---|---|
| `permissions` | No | Global catalog — see `config/permissions.php` / `PermissionSeeder` in ARCHITECTURE.md §3b |
| `roles` | Yes (`company_id` column) | One `Admin` + one `Staff` role per company, auto-seeded by `SeedDefaultRolesForCompany` |
| `model_has_roles`, `model_has_permissions` | Yes (`company_id` in the composite key) | User↔role / user↔permission assignments |
| `role_has_permissions` | No (roles are already company-scoped) | Role↔permission assignments |

`config/permissions.php` is the actual source of truth for which permission names exist — this table just lists what Spatie's package itself creates.

## Module 4 — Settings

`settings` — a generic key/value registry, deliberately **not** following the Module-2-onward conventions above (see ARCHITECTURE.md §3c for why `BelongsToCompany` doesn't fit here).

| Column | Type | Notes |
|---|---|---|
| `uuid` | char(36), unique | Per `HasUuid`, same as every other table |
| `company_id` | BIGINT UNSIGNED, nullable, FK → `companies`, `cascadeOnDelete` | `NULL` means **system-wide** (SaaS-owner scope) — a different meaning than every other nullable `company_id` in this app |
| `key` | string | e.g. `date_format`, `default_trial_days` — see `config/settings.php` for the full catalog |
| `value` | JSON, nullable | Cast to `array` on the model; holds scalars fine (`json_decode` of `"30"` is just the int `30`) |

Indexed on `(company_id, key)` for lookup performance — **not** a uniqueness guarantee (MySQL permits multiple `NULL`s under a composite unique index, so it wouldn't actually stop two system-wide rows sharing a key). `SettingsService::set()` uses `updateOrCreate()` instead, which is correct regardless of that DB-level limitation.

## Module 8 — Storage

No new tables. `companies.storage_disk` (added speculatively in Module 2) is **dropped** by this module's migration — superseded by reading the company's active `integrations` row where `type = 'storage'` instead, since a bare disk name isn't enough for cloud providers (credentials matter too). See ARCHITECTURE.md §5b for `StorageResolver` and how the `integrations.credentials` generic fields are remapped to S3-style bucket/region/endpoint for this type.

## Module 9 — Email

No new tables. Reads the company's active `integrations` row where `type = 'email'` the same way Module 8 reads `type = 'storage'` — the generic `credentials` fields are remapped to Host/Port/Encryption/Username/Password for this type. See ARCHITECTURE.md §5c for `EmailResolver` and why every catalog email provider is treated as SMTP.

## Module 10 — SMS

No new tables. Reads the company's active `integrations` row where `type = 'sms'`. Unlike Storage/Email, the `credentials` field mapping is genuinely different **per provider**, not uniform across the type — see each driver class's docblock in `App\Modules\Sms\Drivers` and ARCHITECTURE.md §5d for the exact mapping and per-provider confidence notes.

## Module 11 — Payments

No new tables. Reads the company's active `integrations` row where `type = 'payment'` for a new charge; `verify`/`refund` instead target an explicit provider's row directly (not necessarily the currently-active one). All 12 catalog providers have a real driver; 5 (Tigo Pesa, HaloPesa, NMB, CRDB, NBC) additionally require a Base URL supplied via the credential form's Password field, since this app has no confirmed public hostname for them. See ARCHITECTURE.md §5e for `PaymentManager`, the credential mapping per driver, and each provider's confidence tier.

## Module 29 — Subscriptions & Billing

`subscription_plans` — `HasUuid`/`SoftDeletes`, but **no `company_id`** — this is a platform-wide catalog, not tenant data.

| Column | Type | Notes |
|---|---|---|
| `name`, `slug` | string | `slug` globally `unique`, auto-generated from `name` on create/update when left blank |
| `description` | text, nullable | |
| `price` | decimal(10,2) | Platform-level money — a smaller precision than the `decimal(12,2)` used for tenant-facing money elsewhere in the app (rent, invoices), since this is the SaaS owner's own price list, not a company's financial data |

`subscriptions` — `HasUuid`, **no `SoftDeletes`, no `BelongsToCompany`** (has a `company_id` column but is accessed via `SubscriptionPolicy`, not a tenant global scope — see ARCHITECTURE.md §22). An immutable history table: rows are never updated except `extendTrial()`'s in-place mutation of `current_period_end`; every plan change or renewal inserts a new row instead.

| Column | Type | Notes |
|---|---|---|
| `company_id` | `FK → companies`, `cascadeOnDelete` | |
| `subscription_plan_id` | `FK → subscription_plans`, `restrictOnDelete` | A plan with active subscribers can't be deleted |
| `status` | enum(`trialing`,`active`,`past_due`,`canceled`), default `trialing` | |
| `current_period_start`, `current_period_end` | date | |
| `canceled_at` | timestamp, nullable | |

Indexed on `(company_id, status)`. `Company::currentSubscription()` resolves "current" via `latest('current_period_start')->latest('id')` — the `id` tie-break matters because `current_period_start` is date-only and two rows created the same calendar day (e.g. a same-day trial-to-paid upgrade) would otherwise tie non-deterministically; see ARCHITECTURE.md §22 for the live bug this caught.

`subscription_invoices` — `HasUuid`/`SoftDeletes`, no `BelongsToCompany` (same reasoning as `subscriptions`). The SaaS owner's own invoice to a company for its platform subscription — a distinct sequence and concept from Module 17's `invoices` table (a company billing its own tenants for rent).
